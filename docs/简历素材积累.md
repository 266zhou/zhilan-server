## A. 技术亮点（可直接转成简历 Bullet）

### A1. 多级缓存（阶段 2）

- **Caffeine（L1 本地）+ Redis（L2 分布式）两级缓存**，热点数据先查本地，本地未命中再查 Redis
- **缓存穿透**：空值缓存（`""` 占位，短 TTL 2 分钟），未命中直接返回，不打数据库
- **缓存击穿**：逻辑过期方案 —— `RedisData` 包装类存"数据 + 过期时间"，key 物理永不过期；逻辑过期后抢 `SETNX` 互斥锁，抢到的线程异步重建，没抢到的直接返回旧数据
  - 对比方案：互斥锁（一致性优先，性能差）vs 逻辑过期（性能优先，短暂不一致）
- **缓存雪崩**：TTL 加随机数，避免同一时刻批量失效
- **Cache Aside**：更新数据库后删除缓存（不是更新缓存）

### A2. 缓存一致性（阶段 2）

- **三层防线**：① 更新 DB 后立刻删缓存 → ② 删失败发 MQ 补偿重试 → ③ TTL 兜底
- **关键细节**：删缓存要放在**事务提交之后**（`TransactionSynchronization.afterCommit()`），
  否则会出现"缓存已删、事务未提交，其他线程读到旧值并写回缓存"的脏数据窗口
- 理解了 **回调（callback）≠ 回滚（rollback）** 的区别；事务回滚时 `afterCommit` 不会执行（正确行为）

### A3. 秒杀防超卖（阶段 3）

- **Redis + Lua 脚本**实现原子"判断库存 + 一人一单 + 扣减"，一次网络往返完成
- **三重兜底**：
  1. Redis + Lua（内存原子，挡住 99.99% 流量）
  2. DB 条件更新 `UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0`（乐观锁思想）
  3. 唯一索引 `uk_user_voucher`（数据库层绝对不重复）
- **一人一单双层防护**：Redis Set（挡流量）+ DB 唯一索引（保正确）
- **压测结果**：200 并发抢 100 张券 → 订单数 100、DB 库存 0、Redis 库存 0、`scard` 100、零重复用户
  → 四个层次数据完全自洽

### A4. MQ 异步下单（阶段 3）

- **RabbitMQ 削峰填谷**：Lua 拦掉无效请求后，只有真正要下单的请求进队列，用户响应时间从 ~26ms 降到 ~2ms
- **消息可靠性四环节全覆盖**：
  - 生产→交换机：`publisher-confirm`
  - 交换机→队列：`publisher-returns`
  - 队列→消费者：**手动 ack**（`basicAck` / `basicNack(requeue=false)`）
  - 队列/消息本身：队列 `durable` + 消息 `PERSISTENT`
- **消费端幂等**：先查重（`count` 只查 `active_flag=1`）+ 唯一索引兜底（`DuplicateKeyException` 捕获后 ack）
- **`prefetch: 1`** 控制预取数量，避免消息堆积在消费者内存里
- 消息转换器必须注入 Spring 的 `ObjectMapper`，否则 `LocalDateTime` 序列化失败

### A5. 订单超时关单 + 乐观锁（阶段 4）

- **Spring Task** `@Scheduled(cron = "0 */1 * * * ?")` 每分钟扫描超时未支付订单
- **乐观锁**（MyBatis-Plus `@Version` + `OptimisticLockerInnerInterceptor`）解决"支付 vs 关单"并发冲突
- **核心原则：先抢关单权，后回补库存**
  - `updateById` 成功（影响行数 1）才回补；失败（影响行数 0）说明别人改了，直接放弃
  - 顺序反了会导致"订单已支付但库存被回补"→ 超卖
- **关单要做的三件事**：`status=3` + `active_flag=NULL`、DB `stock+1`、Redis `stock+1`、Redis `SREM` 用户
- **`@EnableScheduling` 忘了加 → 定时任务静默不执行**（无任何报错，只能靠日志发现）

### A6. `active_flag` 支持"取消后可重购"（阶段 4）⭐ 亮点

- **业务问题**：用户忘记付款导致订单超时关闭，不应该永久剥夺其购买资格
- **技术障碍**：唯一索引 `uk_user_voucher(user_id, voucher_id)` 不看 status，已取消的订单仍占位
- **解法**：利用 **MySQL 唯一索引允许多个 NULL** 的特性，把索引改成三列
  ```sql
  UNIQUE KEY uk_user_voucher (user_id, voucher_id, active_flag)
  ```
  - 有效订单 `active_flag = 1` → 占位，保证"一人一单"
  - 已取消订单 `active_flag = NULL` → 不占位，可以有多条历史记录
- **连带修改 4 处**（这条最关键，体现了"规则散落多处必须对齐"）：
  1. Redis Set 关单时 `SREM`
  2. 消费者查重加 `active_flag = 1`
  3. 关单时 `setActiveFlag(null)`
  4. `getOrderByUser` 加 `active_flag = 1` + `LIMIT 1`（否则 `getOne` 查到多条抛 `TooManyResultsException`）
- **`FieldStrategy.ALWAYS`**：MyBatis-Plus 默认 `NOT_NULL` 会跳过 null 字段，
  不加这个注解 `active_flag` 置不空

## B. 问题 → 定位 → 解决（面试讲故事用）⭐⭐

> 这类素材比"我用了什么技术"值钱得多。面试官爱问"你遇到过什么难题"。

### B1. MySQL REPEATABLE READ 快照导致"冲突后重查"失效（阶段 4）⭐⭐⭐ 最好的一个

- **现象**：并发测试中"关单赢"时，支付失败提示是「订单状态已变更，请刷新后重试」（409 兜底），
  但数据库里订单明明是 `status=3`（已取消），按代码应该提示「订单已超时关闭」
- **定位**：看日志确认走了 `[支付] 乐观锁冲突` 分支，重查后三个 if 分支全不命中
- **根因**：**MySQL InnoDB 默认 `REPEATABLE READ`，事务内第一次 SELECT 建立一致性快照，
  后续普通 SELECT 都读快照** —— 即使别的线程已提交
  - `UPDATE` / `SELECT ... FOR UPDATE` 是**当前读**，能看到最新数据
  - 普通 `SELECT` 是**快照读**，看不到
- **修复**：把重查改成 `SELECT ... FOR UPDATE`（`wrapper.last("FOR UPDATE")`）→ 提示正确
- **为什么只有并发测试能发现**：顺序测试时 `getById` 一开始就读到 `status=3`，走早退分支，根本没进冲突分支
- **收获**：理解了数据库隔离级别对"先写后读"逻辑的实际影响

### B2. `@Version` 导入错包导致乐观锁静默失效（阶段 4）⭐⭐

- **现象**：配置都正确、启动无报错、`updateById` 永远返回 `true`，但乐观锁好像没生效
- **定位**：**看 MyBatis 打印的实际 SQL**
  ```
  UPDATE voucher_order SET ..., version=? WHERE id=?          ← 没有版本条件！
  ```
- **根因**：`import org.springframework.data.annotation.Version`（Spring Data 的）
  而不是 `com.baomidou.mybatisplus.annotation.Version`（MyBatis-Plus 的）。
  IDEA 自动导入默认选了第一个，两个注解同名
- **修复**：改 import → SQL 变成 `WHERE id=? AND version=?`，`version` 从 0 变 1
- **收获**：**"配了 ≠ 生效"。验证插件/拦截器唯一可靠的方法是看它生成的 SQL**

### B3. 幂等逻辑顺序错误，退化成"靠库存不足拦截"（阶段 3）⭐⭐

- **现象**：测试消费端幂等，期望日志是「重复订单，忽略」，实际是「数据库库存不足，Redis 与 DB 不一致」
- **定位**：看日志发现 `UPDATE ... WHERE stock > 0` 返回 `Updates: 0`，在**插订单之前**就抛异常了
- **根因**：`createOrderFromMq` 里**先扣库存、后插订单**，库存为 0 时永远走不到唯一索引那步
- **修复**：把**幂等检查提到最前面**（先查重 → 再扣库存 → 最后插订单）
- **收获**：数据结果正确 ≠ 逻辑正确。日志语义错了会掩盖真异常

### B4. `Result.ok()` 无限递归导致"更新成功却返回 500"（阶段 1）⭐⭐

- **现象**：调用更新接口返回「系统繁忙」，但数据库已经更新成功了
- **定位**：日志里有 `StackOverflowError`，被全局异常处理器兜成 500
- **根因**：`ok()` 方法体里写了 `return ok();`（应该 `return ok(null);`）→ 无限递归
- **收获**：Spring 的 catch-all `@ExceptionHandler(Exception.class)` 会把框架异常也兜成 500，
  排查时**必须看控制台的真实堆栈**，不能只看接口返回

### B5. pom.xml 全部标红，Maven 无法解析（阶段 1）⭐⭐

- **现象**：pom 所有依赖标红，IDEA 提示"更新 Maven 无法解决"
- **根因**：Spring Initializr 按 Spring Boot **4.1.1** 生成了 `spring-boot-starter-*-test` 三个细粒度 test starter，
  但 `<parent>` 版本是 **3.3.5**，这三个 artifact 在 3.3.5 里**不存在**
  - 在 `.m2` 里对比 `spring-boot-dependencies-3.3.5.pom` 和 `-4.1.1.pom` 确认
  - **Maven 依赖解析是 all-or-nothing**：一个解析不了，整个 pom 都不下载
- **修复**：删掉三个不存在的 starter，改回 `spring-boot-starter-test`
- **收获**：学会用本地仓库里的 `spring-boot-dependencies-*.pom` 反查某个 artifact 是否存在

### B6. 测试类放错源码根目录，JUnit 找不到（阶段 4）⭐

- **现象**：`import org.junit.jupiter.api.Test;` 一直标红
- **根因**：测试类放在了 `src/main/java`，而 `spring-boot-starter-test` 的 scope 是 `test`，
  **只对 `src/test/java` 可见**
- **收获**：`src/main/java` 只能看到 compile/runtime 依赖；`src/test/java` 才能看到 test 依赖
  （顺带：测试类放 main 里会被打进生产 JAR）

### B7. 前后端联调中的"操作习惯"类问题（阶段 3/4）

- **问题**：验证一人一单时用 `POST` 请求了 `GET` 接口 → 全局异常处理器兜成 500「系统繁忙」
- **修复**：加 `HttpRequestMethodNotSupportedException` / `NoResourceFoundException` 专用处理器，
  返回 405 / 404 和明确提示
- **收获**：兜底异常要留，但**可预期的错误要单独处理**，让报错信息能指导排查
