## 2. 第 0 步：概念课（必读）

**这节不看懂，后面代码就是天书。** 认真读 15 分钟。

### 2.1 超卖是怎么发生的（先看问题）

假设库存只剩 **1** 件，同时来了 **100 个请求**。如果代码这么写：

```java
// ❌ 典型错误写法
SeckillVoucher voucher = voucherMapper.selectById(id);
if (voucher.getStock() > 0) {              // ① 查库存 = 1，通过
    voucherMapper.updateStock(id, voucher.getStock() - 1);  // ② 扣库存
    orderMapper.insert(order);             // ③ 建订单
}
```

**并发下的真实时序：**

```
时刻   线程A                   线程B                  数据库 stock
────────────────────────────────────────────────────────────────
 t1    ① 查到 stock = 1                                  1
 t2                            ① 查到 stock = 1          1
 t3    ② 扣库存 → 更新为 0                                0
 t4                            ② 扣库存 → 更新为 0        0   ← 又扣了！
 t5    ③ 建订单                                          -1   ← 卖出去 2 件！
 t6                            ③ 建订单                  （超卖）
```

**问题本质**：**"查库存"和"扣库存"是两个分开的操作，中间会被别的线程插进来。**

这叫**「读-改-写」的竞态条件（Race Condition）**。

### 2.2 三种防超卖方案（重点对比）

#### 方案一：悲观锁（`synchronized` / 分布式锁）

**思路**：让请求**排队**，一个一个来。

```java
synchronized (this) {     // 只在单机有效
    checkAndDeduct();
}
```

| 优点 | 缺点 |
|---|---|
| 简单 | ❌ **串行**，10000 个请求要一个个排队，**性能极差** |
| 一定不超卖 | ❌ 单机 `synchronized` 多台服务器就失效了，得用 Redis 分布式锁，更慢 |

**结论**：秒杀场景**不能用**，太慢。

#### 方案二：乐观锁（数据库条件更新）

**思路**："我猜没人改过，扣的时候顺便检查一下"。

```sql
-- 一条 SQL 完成"判断 + 扣减"，靠数据库保证原子性
UPDATE seckill_voucher
SET stock = stock - 1
WHERE id = ? AND stock > 0;     -- ← 关键：stock > 0 作为条件
```

```java
boolean ok = voucherService.update(
    new LambdaUpdateWrapper<SeckillVoucher>()
        .setSql("stock = stock - 1")
        .eq(SeckillVoucher::getId, id)
        .gt(SeckillVoucher::getStock, 0));   // 影响行数=0 说明没库存了
```

| 优点 | 缺点 |
|---|---|
| 一条 SQL，原子 | ❌ 仍然要打数据库，**MySQL 单机扛不住几万 QPS** |
| 简单可靠 | ❌ 失败率高时大量无效请求打库 |

**结论**：**很好的兜底方案**，但作为主流程性能不够。

#### 方案三：Redis + Lua（本项目采用）

**思路**：把"判断库存 + 扣减"放进 **Redis 内存**里，用 **Lua 脚本**保证原子执行。

```
为什么 Lua 能保证原子？
  Redis 是单线程执行命令的。执行 Lua 脚本时，Redis 会把整个脚本
  当成一个"不可分割的命令"执行完，中途不会插入其他客户端的命令。
  → 脚本里的"判断 + 扣减"不会被别的请求打断
```

| 优点 | 缺点 |
|---|---|
| ✅ **内存操作，10 万+ QPS** | Redis 和 MySQL 需要同步（本阶段用 MQ 解决） |
| ✅ 原子，绝不超卖 | 逻辑比前两种复杂 |

**结论**：**秒杀主流程用它，MySQL 的条件更新作为最终兜底。**

#### 📊 三种方案对比表（面试直接背）

| | 悲观锁 | 乐观锁（DB） | **Redis + Lua** |
|---|---|---|---|
| 性能 | 最差（串行） | 中 | **最高** |
| 实现复杂度 | 低 | 低 | 中 |
| 数据一致性 | 强 | 强 | 需要额外同步机制 |
| 适用场景 | 并发低的场景 | 一般业务 | **秒杀/抢购** |

### 2.3 一人一单的难点

**"同一个用户只能买一张券"** —— 这又是一个并发问题：

```
用户A 的两个请求同时到达：
  请求1：查"用户A买过吗" → 没有
  请求2：查"用户A买过吗" → 没有
  请求1：插入订单 ✅
  请求2：插入订单 ✅     ← 买了 2 张！
```

**两种解法，最佳实践是两个都要：**

| 层次 | 手段 | 作用 |
|---|---|---|
| **第一道（快）** | Redis Set：`SADD seckill:order:{voucherId} {userId}` | 在 Lua 里原子判断，**挡住 99.9% 的重复请求** |
| **第二道（准）** | 数据库唯一索引 `UNIQUE KEY (user_id, voucher_id)` | 最终兜底，**保证绝不重复** |

> **为什么两个都要？**
> Redis 快，但可能丢数据（重启/被清空）；数据库准，但慢。
> **Redis 挡流量，数据库保正确** —— 这是秒杀系统的标准做法。

### 2.4 为什么要用 MQ（削峰填谷）

**先看同步版的问题**：

```
瞬间 10 万个请求
    ↓
全部打到应用服务器
    ↓
全部去扣 MySQL 库存、插订单
    ↓
MySQL 连接池瞬间被打爆 → 大量超时 → 用户看到"系统繁忙"
```

**MQ 异步后**：

```
瞬间 10 万个请求
    ↓
Redis + Lua 拦掉 9.99 万个（库存不足/重复下单）
    ↓
只剩 100 个"真正要下单"的请求
    ↓
发 100 条消息进 RabbitMQ（瞬间完成，不碰数据库）
    ↓
立即返回"排队中" ← 用户 50ms 内就得到响应
    ↓
消费者按自己的节奏，慢慢处理这 100 条消息（扣库存、建订单）
```

**这叫「削峰填谷」**：

```
请求量
  │   ████
  │   ████          ← 峰值被 MQ "削"掉了
  │   ████
  │   ████████
  │   ████████████  ← 消费者平稳处理（填谷）
  └──────────────────── 时间
```

### 2.5 整体架构图

```
                        用户请求 POST /seckill/{voucherId}

                    ┌──────────────────────────────┐
                    │  ① Redis + Lua（原子判断）      │
```

## 3. 第 1 步：建表

在 `sql/init.sql` 末尾追加两张表：

```sql
-- ============================================================
-- 阶段 3：秒杀
-- ============================================================

-- 秒杀优惠券
DROP TABLE IF EXISTS `seckill_voucher`;
CREATE TABLE `seckill_voucher` (
    `id`           BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
    `shop_id`      BIGINT       NOT NULL COMMENT '所属商家',
    `title`        VARCHAR(64)  NOT NULL COMMENT '券标题',
    `sub_title`    VARCHAR(128) DEFAULT NULL COMMENT '副标题',
    `stock`        INT          NOT NULL DEFAULT 0 COMMENT '库存',
    `begin_time`   DATETIME     NOT NULL COMMENT '秒杀开始时间',
    `end_time`     DATETIME     NOT NULL COMMENT '秒杀结束时间',
    `pay_value`    BIGINT       NOT NULL DEFAULT 0 COMMENT '支付金额(分)',
    `actual_value` BIGINT       NOT NULL DEFAULT 0 COMMENT '抵扣金额(分)',
    `status`       TINYINT      NOT NULL DEFAULT 1 COMMENT '状态 1上架 0下架',
    `create_time`  DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `update_time`  DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`id`),
    KEY `idx_shop_id` (`shop_id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '秒杀优惠券';

-- 优惠券订单
DROP TABLE IF EXISTS `voucher_order`;
CREATE TABLE `voucher_order` (
    `id`          BIGINT   NOT NULL AUTO_INCREMENT COMMENT '主键',
    `user_id`     BIGINT   NOT NULL COMMENT '下单用户',
    `voucher_id`  BIGINT   NOT NULL COMMENT '优惠券id',
    `status`      TINYINT  NOT NULL DEFAULT 1 COMMENT '1未支付 2已支付 3已取消 4已退款',
    `create_time` DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `pay_time`    DATETIME DEFAULT NULL COMMENT '支付时间',
    `update_time` DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_user_voucher` (`user_id`, `voucher_id`),   -- ⭐ 一人一单的最终兜底
    KEY `idx_voucher_id` (`voucher_id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '优惠券订单';
```

### 3.1 两个关键设计

#### ① `UNIQUE KEY uk_user_voucher (user_id, voucher_id)`

**这是"一人一单"的数据库级保证。** 加了它之后，同一个用户对同一张券第二次插入会直接抛 `DuplicateKeyException` —— **数据库层面绝对不会重复**。

> 这是**最后一道防线**。即使 Redis 全部失效，这一层也能保证不重复。

> ### 📌 阶段 4 会改这个索引
>
> **阶段 4 要支持"订单超时关闭后用户能重新购买"**，所以这个两列索引会被改成三列：
>
> ```sql
> UNIQUE KEY uk_user_voucher (user_id, voucher_id, active_flag)
> ```
>
> 其中 `active_flag = 1`（有效订单）、`active_flag = NULL`（已取消）。
> **利用 MySQL 唯一索引允许多个 NULL 的特性**，让已取消的订单不占位。
>
> **现阶段先按两列建**，到阶段 4 的「第 1 步」再 ALTER。

#### ② `pay_value` / `actual_value` 用 `BIGINT` 存「分」

**金额单位用"分"（整数），不用"元"（小数）。**

```sql
pay_value = 9800     -- 表示 98.00 元
```

**为什么？**
- `BIGINT` 整数运算**没有精度问题**
- 前面阶段用 `DECIMAL` 也行，但**秒杀这种高并发场景，整数运算更快**
- 支付系统普遍这么做（微信、支付宝都是分）

### 5.1 追加 Redis Key 常量

```java

public static final String SECKILL_STOCK_KEY = "seckill:stock:";

/** 秒杀已下单用户集合：seckill:order:{voucherId}（Set 类型） */

/** 秒杀券详情缓存：cache:voucher:{id} */
public static final String CACHE_VOUCHER_KEY = "cache:voucher:";
```

**命名为什么要分开？**
- `seckill:stock:` 和 `seckill:order:` 是**秒杀业务数据**（不设 TTL，活动期间一直存在）
- `cache:` 开头的是**缓存数据**（用于查询加速，有 TTL）

**分开命名，一眼就知道哪些是缓存、哪些是业务状态。** 清理缓存时也不会误删库存。

### 5.2 秒杀 Lua 脚本（核心）

新建文件 `src/main/resources/lua/seckill.lua`：

```lua
-- 秒杀核心脚本：判断库存 + 一人一单 + 扣减库存（原子执行）
-- KEYS[1] = 库存 key       seckill:stock:{voucherId}
-- KEYS[2] = 已下单集合 key  seckill:order:{voucherId}
-- ARGV[1] = 用户 id
--
-- 返回值：
--   0 = 成功
--   1 = 用户已下过单
--   2 = 库存不足
--   3 = 库存未预热（活动未开始或 key 不存在）

-- ① 库存是否存在
local stock = redis.call('get', KEYS[1])
if stock == false then
    return 3
end

-- ② 库存是否充足
if tonumber(stock) <= 0 then
    return 2
end

-- ③ 一人一单：判断用户是否已在集合里
if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then
    return 1
end

-- ④ 扣库存 + 记录用户（这两步也在同一个原子脚本里）
redis.call('decr', KEYS[1])
redis.call('sadd', KEYS[2], ARGV[1])

return 0
```

### 5.3 逐行讲解

**`redis.call('get', KEYS[1])`**
在 Lua 里调用 Redis 命令，相当于在 `redis-cli` 里敲 `get seckill:stock:1`。

**为什么用 `KEYS[]` 和 `ARGV[]` 而不直接把 key 写死？**
这是 **Redis 的规范要求**：Lua 脚本要用参数化的方式传 key，这样：
- Redis 集群模式能正确路由到对应节点
- 避免脚本注入

**`if stock == false then`**
Redis 的 `get` 对不存在的 key 返回 `false`（Lua 里），**不是 nil，也不是字符串 "nil"**。
**这是个高频坑**，写成 `if stock == nil` 会判断失败。

**`tonumber(stock)`**
Redis 返回的值是**字符串类型**（`"100"`），必须转成数字才能比较。

**`redis.call('sismember', KEYS[2], ARGV[1]) == 1`**
判断 `userId` 是否在集合里。**返回值是数字 1 或 0**（不是布尔值）。

**为什么扣库存和记录用户要放在同一个脚本里？**
因为它们必须**同时成功或同时失败**。如果分开写：

```lua
-- ❌ 错误：分两次调用 Redis
redis.call('decr', KEYS[1])     -- 扣了库存
-- → 这里如果程序崩了 / 网络断了
redis.call('sadd', KEYS[2], ARGV[1])  -- 用户没记录成功
-- 结果：库存少了，但用户还能再买一次 → 少卖了
```

**放在一个脚本里，Redis 保证整段原子执行，不会中断。**

新建 `config/LuaScriptConfig.java`：

## 6. 第 4 步：库存预热

### 6.1 为什么要预热

**秒杀的核心逻辑全在 Redis 里**，但库存本来只存在 MySQL 里。

**如果活动开始后才第一次把库存写进 Redis：**

```
00:00:00 活动开始
  ↓
第 1 个请求来了 → Redis 没有 stock key → 返回"未预热" ❌
```

**所以必须在活动开始前，主动把库存写进 Redis。** 这叫**缓存预热（Warm-up）**。

### 6.2 SeckillVoucherService

新建 `service/SeckillVoucherService.java`：

```java
public interface SeckillVoucherService extends IService<SeckillVoucher> {

     * 把数据库库存预热到 Redis
```

新建 `service/impl/SeckillVoucherServiceImpl.java`：

```java
package com.zhilan.zhilanserver.service.impl;

import com.baomidou.mybatisplus.extension.service.impl.ServiceImpl;
import com.zhilan.zhilanserver.common.BusinessException;
import com.zhilan.zhilanserver.constant.RedisKeyConstants;
import com.zhilan.zhilanserver.entity.SeckillVoucher;
import com.zhilan.zhilanserver.mapper.SeckillVoucherMapper;
import com.zhilan.zhilanserver.service.SeckillVoucherService;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;

@Slf4j
@Service
@RequiredArgsConstructor
public class SeckillVoucherServiceImpl
        extends ServiceImpl<SeckillVoucherMapper, SeckillVoucher>
        implements SeckillVoucherService {

    private final StringRedisTemplate stringRedisTemplate;

    @Override
    public void warmUpStock(Long voucherId) {
        SeckillVoucher voucher = getById(voucherId);
        if (voucher == null) {
            throw new BusinessException(404, "优惠券不存在");
        }

        String stockKey = RedisKeyConstants.SECKILL_STOCK_KEY + voucherId;
        String orderKey = RedisKeyConstants.SECKILL_ORDER_KEY + voucherId;

        // 写入库存
        stringRedisTemplate.opsForValue().set(stockKey, String.valueOf(voucher.getStock()));

        // 清空已下单集合（重新预热时应该是全新活动）
        stringRedisTemplate.delete(orderKey);

        log.info("[预热] 券 {} 库存 {} 已写入 Redis", voucherId, voucher.getStock());
    }
}
```

### 6.3 讲解

**为什么库存写 `String.valueOf(...)`？**
`StringRedisTemplate` 只能存字符串。而且 Redis 里存数字用字符串形式，Lua 里 `tonumber()` 转一下就行。

**为什么要 `delete(orderKey)`？**
如果之前测试过、集合里还有用户记录，重新预热时应该清空，模拟"全新活动"。**不加这行，你重测时会发现"所有人都说已经买过了"**。

**注意这里没有设置 TTL** —— 秒杀的库存和订单集合**不能过期**。过期了会导致：
- 库存 key 消失 → 所有请求返回"未预热"
- 集合消失 → 一人一单失效（可以重复买）

### 7.2 VoucherOrderServiceImpl（同步版）

新建 `service/impl/VoucherOrderServiceImpl.java`：

```java
package com.zhilan.zhilanserver.service.impl;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.baomidou.mybatisplus.core.conditions.update.LambdaUpdateWrapper;
import com.baomidou.mybatisplus.extension.service.impl.ServiceImpl;
import com.zhilan.zhilanserver.common.BusinessException;
import com.zhilan.zhilanserver.constant.RedisKeyConstants;
import com.zhilan.zhilanserver.entity.SeckillVoucher;
import com.zhilan.zhilanserver.entity.VoucherOrder;
import com.zhilan.zhilanserver.mapper.VoucherOrderMapper;
import com.zhilan.zhilanserver.service.SeckillVoucherService;
import com.zhilan.zhilanserver.service.VoucherOrderService;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.dao.DuplicateKeyException;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.List;

@Slf4j
@Service
@RequiredArgsConstructor
public class VoucherOrderServiceImpl
        extends ServiceImpl<VoucherOrderMapper, VoucherOrder>
        implements VoucherOrderService {

    private final SeckillVoucherService seckillVoucherService;
    private final StringRedisTemplate stringRedisTemplate;
    private final DefaultRedisScript<Long> seckillScript;

    @Override
    public void seckillVoucher(Long voucherId, Long userId) {
        // ① 执行 Lua：原子判断库存 + 一人一单 + 扣减
        Long result = stringRedisTemplate.execute(
                seckillScript,
                List.of(RedisKeyConstants.SECKILL_STOCK_KEY + voucherId,
                        RedisKeyConstants.SECKILL_ORDER_KEY + voucherId),
                String.valueOf(userId));

        if (result == null) {
            throw new BusinessException(500, "秒杀脚本执行异常");
        }
        switch (result.intValue()) {
            case 1 -> throw new BusinessException(400, "您已经买过了，一人限购一张");
            case 2 -> throw new BusinessException(400, "手慢了，库存已售罄");
            case 3 -> throw new BusinessException(400, "活动未开始或已结束");
            default -> { /* 0 = 成功，继续 */ }
        }

        // ② 数据库操作（独立事务）
        try {
            createOrder(voucherId, userId);
        } catch (Exception e) {
            // 数据库失败了，必须把 Redis 的预扣回滚，否则库存会"凭空消失"
            rollbackRedis(voucherId, userId);
            throw e;
        }
    }

    /**
     * 数据库层：扣库存 + 建订单（必须在事务里）
     */
    @Transactional(rollbackFor = Exception.class)
    public void createOrder(Long voucherId, Long userId) {
        // ② -1 扣减数据库库存（乐观锁兜底：stock > 0）
        boolean deductSuccess = seckillVoucherService.update(
                new LambdaUpdateWrapper<SeckillVoucher>()
                        .setSql("stock = stock - 1")
                        .eq(SeckillVoucher::getId, voucherId)
                        .gt(SeckillVoucher::getStock, 0));

        if (!deductSuccess) {
            throw new BusinessException(400, "库存不足（数据库兜底拦截）");
        }

        // ② -2 创建订单（唯一索引兜底：重复会抛 DuplicateKeyException）
        VoucherOrder order = new VoucherOrder();
        order.setUserId(userId);
        order.setVoucherId(voucherId);
        order.setStatus(VoucherOrder.STATUS_UNPAID);
        save(order);
    }

    /**
     * 把 Redis 里预扣的库存和用户标记回滚
     */
    private void rollbackRedis(Long voucherId, Long userId) {
        try {
            stringRedisTemplate.opsForValue()
                    .increment(RedisKeyConstants.SECKILL_STOCK_KEY + voucherId);
            stringRedisTemplate.opsForSet()
                    .remove(RedisKeyConstants.SECKILL_ORDER_KEY + voucherId, String.valueOf(userId));
            log.warn("[秒杀] 数据库失败，已回滚 Redis 库存。voucherId={}, userId={}", voucherId, userId);
        } catch (Exception ex) {
            log.error("[秒杀] Redis 回滚也失败了，需要人工介入！voucherId={}, userId={}", voucherId, userId, ex);
        }
    }

    @Override
    public VoucherOrder getOrderByUser(Long voucherId, Long userId) {
        return getOne(new LambdaQueryWrapper<VoucherOrder>()
                .eq(VoucherOrder::getVoucherId, voucherId)
                .eq(VoucherOrder::getUserId, userId));
    }
}
```

### 7.3 逐块讲解（重点）

#### ① `stringRedisTemplate.execute(...)` 参数

```java
stringRedisTemplate.execute(
        seckillScript,                              // 要执行的脚本
        List.of(库存key, 集合key),                    // KEYS[1], KEYS[2]（顺序必须对上）
        String.valueOf(userId));                    // ARGV[1]
```

**参数顺序极其重要**：
- `KEYS[]` 是第 2 个参数（List）
- `ARGV[]` 是第 3 个参数（可变参数）

**列表里的顺序 = 脚本里 `KEYS[1]`、`KEYS[2]` 的顺序。写反了会把库存 key 当集合 key 用。**

#### ② 为什么 `createOrder` 要单独一个方法 + `@Transactional`

**这是 Spring 事务的一个大坑**：**同一个类里，方法 A 调用方法 B，`@Transactional` 不生效！**

```java
// ❌ 错误：@Transactional 加在 seckillVoucher 上，但 createOrder 是内部调用
public void seckillVoucher(...) { createOrder(...); }
```

因为 Spring 的事务是通过**代理对象**实现的。`this.createOrder()` 是直接调用本类方法，**绕过了代理**，事务注解完全失效。

**所以这里的做法是**：
- `seckillVoucher` **不加** `@Transactional`（它做的事不止数据库操作）
- `createOrder` 加 `@Transactional`，让它成为一个独立事务

**但等等——同样是 `this.createOrder(...)` 内部调用，为什么这里就能生效？**

严格来说**这里也有问题**。正确写法应该是：
- 把 `createOrder` 放到**另一个 Service** 里，注入后调用
- 或者注入自己（`@Lazy` + self）

**为了教程简洁，这里先这样写。** 你要知道：**如果后面发现数据库操作没有回滚，问题就出在这里。**

> **更好但稍复杂的写法**（推荐你了解）：
> ```java
> @Service
> public class VoucherOrderServiceImpl {
>     @Lazy
>     @Autowired
>     private VoucherOrderService self;   // 注入自己的代理
>     
>     public void seckillVoucher(...) {
>         self.createOrder(...);          // ← 走代理，事务生效
>     }
> }
> ```

#### ③ 数据库的两层兜底，必须理解

**库存兜底：**

```java
.setSql("stock = stock - 1")     // 原子自减
.gt(SeckillVoucher::getStock, 0) // 只有 stock > 0 才更新
```

**转成 SQL 是：**

```sql
UPDATE seckill_voucher SET stock = stock - 1 WHERE id = ? AND stock > 0
```

**如果影响行数是 0**，说明库存已经没了 —— 即使 Redis 判断有库存，数据库这一层也会拦住。**这是防超卖的最后一道防线。**

**一人一单兜底：**

```java
save(order);   // 触发 UNIQUE KEY 冲突 → DuplicateKeyException
```

**这两层兜底的意义**：Redis 可能因为重启、被清空等原因出问题，但**数据库永远不会算错**。

#### ④ `rollbackRedis` 为什么必须有（重要）

**看这个场景**：

```
① Lua 执行成功 → Redis 库存从 100 减到 99，用户记录进集合
② 数据库扣库存 —— 成功了
③ 数据库插订单 —— 抛异常（比如连接断了）
```

**结果**：Redis 里库存少了 1 个，但数据库里没有这个订单 → **这 1 张券"凭空消失"了，永远卖不出去。**

**所以数据库操作失败时，必须把 Redis 的预扣回滚回去。**

| 回滚动作 | 作用 |
|---|---|
| `increment(stockKey)` | 库存 +1 |
| `srem(orderKey, userId)` | 把用户从"已下单"集合移除 |

**注意 `rollbackRedis` 用 `try-catch` 包了一层** —— 如果连回滚都失败了，要打 `error` 日志留给人工处理。**这种"双向失败"是最难排查的。**

#### ⑤ `switch` 的新写法

```java
switch (result.intValue()) {
    case 1 -> throw new BusinessException(400, "...");
    case 2 -> throw new BusinessException(400, "...");
    default -> { /* 0 = 成功 */ }
}
```

Java 14+ 的箭头式 switch，不用写 `break`。`default -> { }` 是空语句块，表示"0 的情况什么也不做，继续往下走"。

# Part B：RabbitMQ 异步下单

## 10. 第 8 步：为什么同步版不够用

### 10.1 同步版的瓶颈在哪

Part A 完成后，虽然**正确性**没问题（不超卖、一人一单），但**性能**有问题：

```
单个请求的耗时：
  Redis + Lua 判断     ≈ 1ms
  扣 MySQL 库存         ≈ 10ms
  插 MySQL 订单         ≈ 10ms
  事务提交              ≈ 5ms
  ─────────────────────────
  合计                 ≈ 26ms
```

**如果库存有 10000 张、来了 10 万个请求：**

```
能通过的 10000 个请求 × 26ms = 每个请求都要完整走一遍数据库
       ↓
并发 200 个请求 → 200 个同时抢 MySQL 连接池
       ↓
连接池只有 10 个连接 → 190 个等待 → 大量超时
       ↓
用户看到"系统繁忙"、500 错误
```

**这就是"同步"的问题：所有耗时操作都压在请求线程里，用户必须等。**

### 10.2 异步改造的思路

```
【同步】用户 → Redis判断 → 扣库 → 建单 → 返回        （用户等 26ms）
【异步】用户 → Redis判断 → 发MQ → 返回"排队中"       （用户只等 2ms）
                                    ↓
                            消费者慢慢扣库、建单
```

| 对比项 | 同步版 | 异步版 |
|---|---|---|
| 用户等待 | 26ms | **~2ms** |
| 数据库压力 | 请求有多大就压多大 | **受消费者数量控制** |
| 峰值处理 | 直接被压垮 | **MQ 排队，削峰** |
| 复杂度 | 简单 | 需要处理消息可靠性 |

### 10.3 改造范围（好消息）

**只需要改 3 个东西**：

| 改什么 | Part A 的状态 | Part B 改成 |
|---|---|---|
| `seckillVoucher` 方法 | 同步建单 | 发 MQ |
| 新增 MQ 生产者/消费者 | 无 | 新增 |
| Controller / 查订单接口 | 已有 | **完全不用改** ✅ |

**这又是一次"接口不变、实现升级"。**

## 11. 第 9 步：RabbitMQ 配置

### 11.1 先改一下 application.yaml（重要）

你阶段 1 配的 `application.yaml` 里有这段：

```yaml
  rabbitmq:
    ...
    listener:
      simple:
        acknowledge-mode: manual         # 消费者手动 ack
        retry:
          enabled: true                  # ← 这个会和"手动 ack"冲突
          max-attempts: 3
```

**⚠️ `retry.enabled: true` + `acknowledge-mode: manual` 会互相打架。**

`retry` 是 Spring 帮你自动重试（失败后重新调用监听方法），而 `manual ack` 是我们自己控制确认。两者混用行为很难预测，**新手极容易踩坑**。

**改成这样**（关掉自动重试，我们自己控制）：

```yaml
  rabbitmq:
    host: ${RABBITMQ_HOST:localhost}
    port: ${RABBITMQ_PORT:5672}
    username: ${RABBITMQ_USER:guest}
    password: ${RABBITMQ_PASSWORD:guest}
    virtual-host: ${RABBITMQ_VHOST:/}
    publisher-confirm-type: correlated   # 发送端确认
    publisher-returns: true              # 路由失败回退
    listener:
      simple:
        acknowledge-mode: manual         # 手动 ack
        prefetch: 1                      # 每个消费者一次只取 1 条，避免堆积在内存
```

**新增 `prefetch: 1` 的说明**：告诉 RabbitMQ"先给我 1 条，处理完再给我下一条"。**不加的话，RabbitMQ 会一次推很多条过来，消费者处理不过来就全堆在内存里。**

### 11.2 RabbitMQConfig（声明交换机/队列/绑定）

新建 `config/RabbitMQConfig.java`：

```java
package com.zhilan.zhilanserver.config;

import com.fasterxml.jackson.databind.ObjectMapper;
import org.springframework.amqp.core.Binding;
import org.springframework.amqp.core.BindingBuilder;
import org.springframework.amqp.core.DirectExchange;
import org.springframework.amqp.core.Queue;
import org.springframework.amqp.core.QueueBuilder;
import org.springframework.amqp.support.converter.Jackson2JsonMessageConverter;
import org.springframework.amqp.support.converter.MessageConverter;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

/**
 * RabbitMQ 配置：声明秒杀相关交换机、队列、绑定
 */
@Configuration
public class RabbitMQConfig {

    /** 秒杀交换机 */
    public static final String SECKILL_EXCHANGE = "seckill.exchange";
    /** 秒杀订单队列 */
    public static final String SECKILL_ORDER_QUEUE = "seckill.order.queue";
    /** 路由键 */
    public static final String SECKILL_ORDER_ROUTING_KEY = "seckill.order";

    /**
     * 直连交换机（Direct）：按 routing key 精确匹配投递
     */
    @Bean
    public DirectExchange seckillExchange() {
        // 参数：名称, durable(是否持久化), autoDelete(无队列绑定时是否自动删除)
        return new DirectExchange(SECKILL_EXCHANGE, true, false);
    }

    /**
     * 订单队列：durable=true 保证 RabbitMQ 重启后队列还在
     */
    @Bean
    public Queue seckillOrderQueue() {
        return QueueBuilder.durable(SECKILL_ORDER_QUEUE).build();
    }

    /**
     * 绑定：把队列绑到交换机，指定 routing key
     */
    @Bean
    public Binding seckillOrderBinding() {
        return BindingBuilder.bind(seckillOrderQueue())
                .to(seckillExchange())
                .with(SECKILL_ORDER_ROUTING_KEY);
    }

    /**
     * 消息转换器：把 Java 对象转成 JSON 传输
     * 注意：要注入 Spring Boot 的 ObjectMapper，否则 LocalDateTime 会序列化失败
     */
    @Bean
    public MessageConverter jsonMessageConverter(ObjectMapper objectMapper) {
        return new Jackson2JsonMessageConverter(objectMapper);
    }
}
```

### 11.3 讲解

**`DirectExchange` 是什么？**
RabbitMQ 有四类交换机，最常用两种：

| 类型 | 路由方式 | 场景 |
|---|---|---|
| **Direct** | 按 routing key **精确匹配** | 我们用它（`seckill.order` → 秒杀队列） |
| **Fanout** | **广播**给所有绑定队列 | 广播通知、缓存失效通知 |
| Topic | 按通配符匹配（`order.*`） | 复杂路由 |

**`durable=true` 为什么重要？**
队列不持久化的话，RabbitMQ 一重启队列就没了，消息全丢。**生产环境必须持久化。**

**为什么 `MessageConverter` 要注入 `ObjectMapper`？**
```java
new Jackson2JsonMessageConverter()          // ❌ 用默认 ObjectMapper
new Jackson2JsonMessageConverter(objectMapper)  // ✅ 用 Spring 配好的
```

默认的 `ObjectMapper` **不认识 `LocalDateTime`**，消息体里只要有时间字段就抛异常：
```
Java 8 date/time type LocalDateTime not supported by default
```
注入 Spring Boot 的就自动带 `JavaTimeModule`，省心。

**`@Bean` 声明交换机和队列有什么好处？**
应用启动时，如果 RabbitMQ 里没有这些交换机/队列，**Spring 会自动创建**。
好处：不用手动去 RabbitMQ 管理后台点，代码即配置。

> **可以在 `http://localhost:15672` → Queues 页面看到自动创建的队列。**

### 12.2 生产者

新建 `mq/SeckillOrderProducer.java`：

```java
package com.zhilan.zhilanserver.mq;

import com.zhilan.zhilanserver.config.RabbitMQConfig;
import com.zhilan.zhilanserver.dto.SeckillOrderMessage;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.amqp.rabbit.core.RabbitTemplate;
import org.springframework.stereotype.Component;

/**
 * 秒杀订单消息生产者
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class SeckillOrderProducer {

    private final RabbitTemplate rabbitTemplate;

    public void sendSeckillOrder(SeckillOrderMessage message) {
        rabbitTemplate.convertAndSend(
                RabbitMQConfig.SECKILL_EXCHANGE,
                RabbitMQConfig.SECKILL_ORDER_ROUTING_KEY,

        log.info("[MQ] 已发送秒杀订单消息 voucherId={}, userId={}",

```

### 12.3 讲解

**`RabbitTemplate`** 是 Spring 提供的"发消息工具类"，和 `StringRedisTemplate` 是同一个思路。**Spring Boot 自动配置好了，直接注入就能用。**

**`convertAndSend(交换机, routingKey, 对象)`**：
- 会把对象用 `MessageConverter` 转成 JSON
- 然后发给指定的交换机 + routing key

**重要概念：消息是发给"交换机"的，不是直接发给"队列"。**

```
生产者 → 交换机(seckill.exchange) → 按 routingKey 找匹配的队列 → 队列(seckill.order.queue) → 消费者
```

**为什么要经过交换机这一层？** 为了灵活：一个交换机可以绑多个队列（广播）、可以按不同 routing key 分发到不同队列。

## 13. 第 11 步：MQ 消费者

新建 `mq/SeckillOrderConsumer.java`：

```java
package com.zhilan.zhilanserver.mq;

import com.rabbitmq.client.Channel;
import com.zhilan.zhilanserver.config.RabbitMQConfig;
import com.zhilan.zhilanserver.dto.SeckillOrderMessage;
import com.zhilan.zhilanserver.service.VoucherOrderService;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.amqp.core.Message;
import org.springframework.amqp.rabbit.annotation.RabbitListener;
import org.springframework.dao.DuplicateKeyException;
import org.springframework.stereotype.Component;

import java.io.IOException;

/**
 * 秒杀订单消息消费者
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class SeckillOrderConsumer {

    private final VoucherOrderService voucherOrderService;

    @RabbitListener(queues = RabbitMQConfig.SECKILL_ORDER_QUEUE)
    public void handleSeckillOrder(SeckillOrderMessage message, Channel channel, Message amqpMessage)
            throws IOException {

        long deliveryTag = amqpMessage.getMessageProperties().getDeliveryTag();
        log.info("[MQ] 收到订单消息 voucherId={}, userId={}",
                message.getVoucherId(), message.getUserId());

        try {
            voucherOrderService.createOrderFromMq(message);
            // 处理成功 → 告诉 RabbitMQ "这条我处理完了，可以删了"
            channel.basicAck(deliveryTag, false);

        } catch (DuplicateKeyException e) {
            // 重复消费 / 用户已经下过单 → 幂等，直接确认，不重试
            log.warn("[MQ] 重复订单，忽略 voucherId={}, userId={}",
                    message.getVoucherId(), message.getUserId());
            channel.basicAck(deliveryTag, false);

        } catch (Exception e) {
            log.error("[MQ] 处理订单失败 voucherId={}, userId={}",
                    message.getVoucherId(), message.getUserId(), e);
            // 拒绝消息，requeue=false 表示不重新入队（避免无限重试打爆日志）
            channel.basicNack(deliveryTag, false, false);
        }
    }
}
```

### 13.1 讲解

**`@RabbitListener(queues = "...")`**
声明"这个方法监听这个队列"。队列里有消息时，Spring 会自动调用这个方法。

**三个参数：**
| 参数 | 作用 |
|---|---|
| `SeckillOrderMessage message` | **消息体**（Spring 会自动从 JSON 反序列化） |
| `Channel channel` | RabbitMQ 的原生 Channel，用来 ack/nack |
| `Message amqpMessage` | 原始消息对象，用来取 `deliveryTag` |

**`deliveryTag` 是什么？**
RabbitMQ 给每条消息编的号。ack 的时候要告诉它"我确认的是哪一条"。

**`basicAck(deliveryTag, false)`** = 确认消息已处理
- 第二个参数 `multiple=false` 表示"只确认这一条"（true 表示确认到这条为止的所有）

**`basicNack(deliveryTag, false, false)`** = 拒绝消息
- 第 2 个参数 `requeue=false`：**不重新入队**
- 如果设为 `true`，消息会被重新放回队列，**可能导致死循环**（一直失败一直重试）

**⚠️ 这里有个重要决策：失败了到底要不要重回队列？**

| 选择 | 后果 |
|---|---|
| `requeue=true` | 可能无限重试 → 日志爆炸、队列堵塞 |
| `requeue=false` | 消息丢弃（或进死信队列）→ **需要人工补偿** |

**我们选 `false`**（避免死循环），**并说明生产环境应该配"死信队列"**：失败的消息进入另一个队列，人工或定时任务处理。

### 13.2 幂等：为什么重复消费不会出错

**RabbitMQ 保证"至少一次"投递（at-least-once）**，也就是**可能重复投递**。所以消费者必须**幂等**。

**我们的幂等靠什么？数据库唯一索引。**

```
第一次消费：插入订单成功 ✅
第二次消费（重复投递）：插入订单 → DuplicateKeyException → 捕获 → ack（忽略）
```

**结果：不会产生两条订单。** 靠数据库约束比靠代码判断更可靠。

### 13.3 在 Service 里新增 createOrderFromMq

在 `VoucherOrderService` 接口里新增：

```java
/**
 * 从 MQ 消息创建订单（消费者调用）
 */
void createOrderFromMq(SeckillOrderMessage message);
```

在 `VoucherOrderServiceImpl` 里实现：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void createOrderFromMq(SeckillOrderMessage message) {
    Long voucherId = message.getVoucherId();
    Long userId = message.getUserId();

    // ① 【幂等检查】订单已存在就直接返回
    long exists = count(new LambdaQueryWrapper<VoucherOrder>()
            .eq(VoucherOrder::getUserId, userId)
            .eq(VoucherOrder::getVoucherId, voucherId));
    if (exists > 0) {
        log.info("[MQ] 订单已存在，跳过处理（幂等）voucherId={}, userId={}", voucherId, userId);
        return;   // 正常返回 → 消费者会 basicAck
    }

    // ② 扣数据库库存（乐观锁兜底）
    boolean deductSuccess = seckillVoucherService.update(
            new LambdaUpdateWrapper<SeckillVoucher>()
                    .setSql("stock = stock - 1")
                    .eq(SeckillVoucher::getId, voucherId)
                    .gt(SeckillVoucher::getStock, 0));

    if (!deductSuccess) {
        // 走到这里才是真异常：Redis 判断有库存，但 DB 已经没了
        log.error("[MQ] 数据库库存不足，Redis 与 DB 不一致！voucherId={}", voucherId);
        throw new BusinessException(500, "数据库库存不足");
    }

    // ③ 创建订单（唯一索引兜底，重复会抛 DuplicateKeyException）
    VoucherOrder order = new VoucherOrder();
    order.setUserId(userId);
    order.setVoucherId(voucherId);
    order.setStatus(VoucherOrder.STATUS_UNPAID);
    save(order);
}
```

> #### ⚠️ 为什么必须先做「幂等检查」，不能先扣库存
>
> **错误顺序（先扣库存）：**
> ```
> 重复消息 → 扣库存（stock=0 时失败）→ 抛"库存不足"
>                                     → 永远走不到唯一索引那一步
>                                     → 日志刷一堆误导性的 ERROR
> ```
>
> **正确顺序（先查重）：**
> ```
> 重复消息 → 查到已存在 → return → ack
>                                   → 不扣库存、不报错、日志干净 ✅
> ```
>
> **这是真实踩过的坑**：测幂等时日志显示 `[MQ] 数据库库存不足，Redis 与 DB 不一致！`，
> 但实际 Redis 和 DB 的 stock 都是 0，**完全一致**，只是"没库存可扣"而已。
> **顺序错了，幂等就退化成"靠库存不足拦截"，语义完全不对，而且真异常会被淹没。**
>
> #### 两道幂等防线
>
> | 防线 | 位置 | 作用 |
> |---|---|---|
> | **① 显式查重** | 方法开头 | 主动挡住重复消息（快路径） |
> | **② 唯一索引** | `save()` 时 | 兜底：①③ 之间被并发插入时由 DB 拦住 |
>
> 消费者里的 `catch (DuplicateKeyException)` 依然要保留 —— 它是第二道防线的最后保障。

**注意 `@Transactional` 在这里能生效**，因为它是**从消费者（另一个类）调用的**——走的是 Spring 代理，不是内部调用。

> 这正好印证前面说的"内部调用事务不生效"的问题：**跨类调用就没问题。**

`createOrder` 和 `rollbackRedis` 在 Part B 里**不再需要了**。


> **注意**：如果 Part A 里你用了 `this.createOrder(...)` 内部调用，现在删掉它正好。
> 而且 **Part B 里 Redis 回滚也不需要了** —— 因为数据库失败时，消息会被 nack 丢弃，Redis 预扣的库存**不会回滚**。这是一个已知的取舍（见下面"可靠性加固"里的说明）。

### 14.3 ⚠️ 一个必须知道的取舍

**异步化后，"数据库失败回滚 Redis"变得困难了**：

```
Part A：DB 失败 → 同一个线程里立刻回滚 Redis ✅
Part B：DB 失败发生在【另一个线程】（消费者），
        它没法知道"这个用户的 Redis 预扣该不该回滚"
```

**现状**：DB 失败时消息被丢弃，Redis 库存**少了一个但谁也没买到** → 这个券就"消失"了。

**这就是用异步换性能的代价。** 生产环境的处理方式：

| 方案 | 说明 |
|---|---|
| **死信队列 + 人工补偿** | 失败消息进死信，运维定期处理 |
| **定时对账** | 定时任务比对 Redis 库存 vs DB 库存，发现不一致就修正 |
| **超时未支付自动回补** | 阶段 4 的定时关单任务会回补库存，自然修正 |

**我们会在阶段 4 用"定时关单回补库存"来兜底这个问题。** 现在先知道这个取舍就行。

## 16. 第 14 步：可靠性加固

**这一节讲"消息会不会丢"，面试常问，理解即可。**

### 16.1 消息可能在哪丢

```
生产者 → [①] → 交换机 → [②] → 队列 → [③] → 消费者
```

| 环节 | 可能的问题 | 解决 |
|---|---|---|
| **① 生产 → 交换机** | 网络断了，消息没到 | **publisher-confirm** |
| **② 交换机 → 队列** | routing key 找不到队列，消息被丢弃 | **publisher-returns** |
| **③ 队列 → 消费者** | 消费者拿到消息后崩了 | **手动 ack** |
| 队列本身 | RabbitMQ 重启，队列没了 | **队列持久化**（已做） |
| 消息本身 | RabbitMQ 重启，消息没了 | **消息持久化** |

### 16.2 生产者确认（confirm 回调）

你已经在 `application.yaml` 里配了 `publisher-confirm-type: correlated`。现在把回调用起来：

```java
package com.zhilan.zhilanserver.mq;

import org.springframework.amqp.rabbit.connection.ConnectionFactory;
import org.springframework.amqp.rabbit.core.RabbitTemplate;
import org.springframework.stereotype.Component;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;

import jakarta.annotation.PostConstruct;

@Slf4j
@Component
@RequiredArgsConstructor
public class RabbitConfirmCallback {

    private final RabbitTemplate rabbitTemplate;

    @PostConstruct
    public void init() {
        // ① 消息到达交换机 → 回调成功/失败
        rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
            if (ack) {
                log.debug("[MQ] 消息已到达交换机");
            } else {
                log.error("[MQ] 消息未到达交换机！原因: {}", cause);
                // 生产环境：落库重试 / 告警
            }
        });

        // ② 消息到了交换机但如果找不到队列 → 回调
        rabbitTemplate.setReturnsCallback(returned -> {
            log.error("[MQ] 消息路由失败！交换机={}, routingKey={}, 原因={}",
                    returned.getExchange(), returned.getRoutingKey(),
                    returned.getReplyText());
        });
    }
}
```

**`confirm` 和 `return` 的区别**：

```
confirm：消息"到没到交换机"
return： 消息"到了交换机，但有没有成功进队列"
```

**两个都要配**，否则"消息丢了"你完全不知道。

**生产环境的完整方案**：把发送失败的消息存进数据库（本地消息表），由定时任务重试。这叫「**本地消息表 + 定时补偿**」。

### 16.3 消费者手动 ack（已做）

你已经用了 `basicAck` / `basicNack`，这是第三个保障。

**核心原则**：
```
只有在【真正处理成功】之后才 ack
处理失败 → nack（不重回队列，进死信）
```

### 16.4 幂等（已做，靠唯一索引）

**"至少一次投递"意味着必须幂等。** 你的唯一索引已经解决了。

> **面试标准答案**：
> "RabbitMQ 保证 at-least-once，可能重复投递，所以消费端必须幂等。我们的订单表有 `(user_id, voucher_id)` 唯一索引，重复插入会抛异常，代码捕获后直接 ack，天然幂等。"

## 17. 第 15 步：附加——删缓存失败的 MQ 补偿

**这一步是为了补齐阶段 2 留下的 TODO**（"删缓存失败 → MQ 补偿重试"）。

### 17.1 问题回顾

阶段 2 的 `ShopServiceImpl.updateShop`：

```java
updateById(shop);
cacheClient.delete(key);   // ← 如果这行失败了，缓存就是旧数据
```

**如果 Redis 挂了或网络抖动，`delete` 会抛异常，但数据库已经改了** → 缓存不一致。

### 17.2 解决方案：删失败 → 发 MQ → 消费者重试

**思路**：
```
删缓存成功 → 结束
删缓存失败 → 发一条"删缓存"消息进 MQ
          → 消费者收到后重试删除
          → 还失败 → 记录 + TTL 兜底
```

### 17.3 新增交换机/队列

在 `RabbitMQConfig` 里追加：

```java
    /** 缓存删除补偿队列 */
    public static final String CACHE_DEL_QUEUE = "cache.delete.queue";
    public static final String CACHE_DEL_ROUTING_KEY = "cache.delete";

    @Bean
    public Queue cacheDeleteQueue() {
        return QueueBuilder.durable(CACHE_DEL_QUEUE).build();
    }

    @Bean
    public Binding cacheDeleteBinding() {
        return BindingBuilder.bind(cacheDeleteQueue())
                .to(seckillExchange())     // 复用同一个交换机
                .with(CACHE_DEL_ROUTING_KEY);
    }
```

### 17.4 生产者 + 消费者

```java
// 生产者（放在 SeckillOrderProducer 里，或新建一个）
public void sendCacheDelete(String cacheKey) {
    rabbitTemplate.convertAndSend(
            RabbitMQConfig.SECKILL_EXCHANGE,
            RabbitMQConfig.CACHE_DEL_ROUTING_KEY,
            cacheKey);
    log.warn("[MQ] 缓存删除失败，已发补偿消息 key={}", cacheKey);
}
```

```java
// 消费者
@RabbitListener(queues = RabbitMQConfig.CACHE_DEL_QUEUE)
public void handleCacheDelete(String cacheKey, Channel channel, Message amqpMessage)
        throws IOException {
    long deliveryTag = amqpMessage.getMessageProperties().getDeliveryTag();
    try {
        cacheClient.delete(cacheKey);
        log.info("[MQ] 缓存补偿删除成功 key={}", cacheKey);
        channel.basicAck(deliveryTag, false);
    } catch (Exception e) {
        log.error("[MQ] 缓存补偿删除仍失败 key={}，将依赖 TTL 兜底", cacheKey, e);
        channel.basicAck(deliveryTag, false);   // 不再重试，靠 TTL
    }
}
```

### 17.5 改造 updateShop

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void updateShop(Shop shop) {
    if (shop.getId() == null) {
        throw new BusinessException(400, "id 不能为空");
    }
    updateById(shop);

    String cacheKey = RedisKeyConstants.CACHE_SHOP_KEY + shop.getId();
    try {
        cacheClient.delete(cacheKey);
    } catch (Exception e) {
        // 删缓存失败 → 发 MQ 补偿
        log.error("[缓存] 删除失败，转 MQ 补偿 key={}", cacheKey, e);
        cacheDeleteProducer.sendCacheDelete(cacheKey);
    }
}
```

| 防线 | 已实现 |
|---|---|
| ① 更新库后立刻删缓存 | ✅ |
| ② **删失败 → MQ 补偿重试** | ✅ 本步 |
| ③ TTL 兜底 | ✅ 逻辑过期 30 分钟 |

**至此，简历上那句"更新数据库后删除缓存，若删除失败消息队列补偿重试，TTL 兜底共同保证数据一致性"就完全实现了。**

## 附录：核心知识点速查

| 概念 | 一句话 |
|---|---|
| 超卖 | 并发下"查库存"和"扣库存"分开执行，被其他线程插入 |
| 悲观锁 | 让请求排队，性能差 |
| 乐观锁（DB） | `UPDATE ... SET stock=stock-1 WHERE stock>0`，原子 |
| **Redis + Lua** | 内存原子操作，QPS 最高，秒杀首选 |
| 一人一单 | Redis Set（挡流量）+ DB 唯一索引（保正确） |
| 削峰填谷 | MQ 把瞬时高峰排队化，保护数据库 |
| 消息丢失 | confirm（到交换机）+ return（进队列）+ 持久化 + 手动 ack |
| 幂等 | 重复消费不产生副作用，靠唯一索引 |
| 死信队列 | 处理失败的消息转存，人工/定时补偿 |
