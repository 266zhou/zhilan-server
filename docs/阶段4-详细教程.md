## 2. 第 0 步：概念课（必读）

### 2.1 为什么未支付订单要自动关闭

**场景**：

```
用户 A 抢到券 → 订单创建成功 → 库存 -1
    ↓
但是 A 不付款，也不取消
    ↓
这张券就一直被 A "占着"
    ↓
其他用户想买也买不到（库存已经是 0 了）
```

**所以需要**：**超过一定时间（比如 15 分钟）还没支付，就自动关闭订单，并把库存还回去。**

**这叫「订单超时自动关闭」，也叫「订单回滚」「库存释放」。**

### 2.2 ⚠️ 核心难点：支付和关单会"撞车"

**假设**：订单 15 分钟超时。用户在第 **14 分 59 秒** 点了支付。

```
时刻 14:59:59    用户点支付 → 支付请求发往服务器
时刻 15:00:00    定时任务扫描到"这个订单超时了" → 开始关单
```

**两个线程同时操作同一个订单：**

```
线程 A（支付）                      线程 B（定时关单）
─────────────────────────────────────────────────────────
① 读订单 status = 1（未支付）
                                    ① 读订单 status = 1（未支付）
② UPDATE status = 2（已支付）
                                    ② UPDATE status = 3（已取消）  ← 覆盖了！
                                    ③ 库存 +1（回补）
─────────────────────────────────────────────────────────
最终：status = 3（已取消），但用户的钱已经被扣了 💀
      而且库存被回补了 → 这张券可以再卖一次 → 超卖！
```

**这就是"支付和关单的并发冲突"。**

### 2.3 如果完全不加控制会怎样（三个灾难场景）

| 场景 | 后果 |
|---|---|
| **支付成功，订单却被关** | 用户付了钱拿不到券，客诉 + 退款 |
| **关单回补库存后，用户又支付成功** | 一张券卖两次 → **超卖** |
| **同一个订单被关两次** | 库存 +2 → **超卖** |

**所以必须保证**：**一个订单的状态只能发生一次有效变更。**

### 2.4 解法：乐观锁（Compare And Swap）

#### 核心思想

> **更新的时候，带上"我看到的旧状态"作为条件。**
> **如果条件不成立（说明别人改过了），更新失败，我就放弃。**

#### 一条 SQL 就能做到

```sql
UPDATE voucher_order
SET status = 3
WHERE id = 100 AND status = 1;
--                ^^^^^^^^^^ 关键：只有还是"未支付"才能关闭
```

**用影响行数判断结果：**

| 影响行数 | 含义 | 该做什么 |
|---|---|---|
| **1** | 我成功把状态从 1 改成了 3 | ✅ 继续（回补库存） |
| **0** | 状态已经不是 1 了（被支付了 / 被别人关了） | ❌ 放弃，什么都不做 |

**这就是"乐观锁"**：**不加锁，先干了再说，用条件保证只有一个人能成功。**

#### 完整推演（支付先到）

```
线程 A（支付）                  线程 B（关单）
─────────────────────────────────────────────────────
UPDATE SET status=2
WHERE id=100 AND status=1
→ 影响 1 行 ✅ 成功

                                UPDATE SET status=3
                                WHERE id=100 AND status=1
                                → 影响 0 行 ❌ 失败
                                → 放弃关单，不回补库存

最终：status = 2（已支付），库存不回补 ✅ 完全正确
```

#### 完整推演（关单先到）

```
线程 A（支付）                  线程 B（关单）
─────────────────────────────────────────────────────
                                UPDATE SET status=3
                                WHERE id=100 AND status=1
                                → 影响 1 行 ✅ 成功
                                → 回补库存 ✅

UPDATE SET status=2
WHERE id=100 AND status=1
→ 影响 0 行 ❌ 失败
→ 提示"订单已关闭，无法支付"

最终：status = 3（已取消），库存已回补，用户没付钱 ✅ 正确
```

**关键洞察**：

> **谁先 UPDATE 成功，谁就"抢到"了这个订单的处理权。另一个人自动放弃。**
> **数据库的行锁保证这两个 UPDATE 是串行的，不会同时成功。**

### 2.5 乐观锁 vs 悲观锁

| | 悲观锁 | 乐观锁 |
|---|---|---|
| **思路** | 先锁住，别人等着 | 不加锁，更新时检查 |
| **实现** | `SELECT ... FOR UPDATE`、分布式锁 | `WHERE version = ?` / `WHERE status = ?` |
| **性能** | 差（串行等待） | **好（并发）** |
| **冲突多时** | 好（等一会儿就好） | 差（大量失败重试） |
| **冲突少时** | 浪费（白锁） | **好** |
| **适用场景** | 库存扣减、账户扣款 | **订单状态变更** ← 我们的场景 |

**为什么订单用乐观锁？**

> **一个订单只会被支付一次、被关一次，"支付 vs 关单"撞上的概率极低。**
> 冲突少 → 乐观锁最优，因为绝大多数请求都一次成功，不用等待。

> ⚠️ **注意区分**：阶段 3 的库存扣减用的是 `WHERE stock > 0` 的条件更新，**那也是乐观锁的思想**。
> 只是库存冲突**很多**（100 人抢 10 张，90 个会失败），所以靠 Redis + Lua 先把流量挡掉。

### 2.6 两种乐观锁写法：version 字段 vs 状态字段

#### 写法 A：version 字段（通用方案）

```sql
-- 先查
SELECT id, status, version FROM voucher_order WHERE id = 100;   -- version = 0

-- 再改（带版本条件）
UPDATE voucher_order
SET status = 3, version = version + 1
WHERE id = 100 AND version = 0;
```

| 优点 | 缺点 |
|---|---|
| **通用**：任何表都能加 | 要**先查一次**再改（2 次 SQL） |
| 不依赖业务字段 | 需要维护 `@Version` 注解 |

#### 写法 B：状态字段做 CAS（更轻量）

```sql
UPDATE voucher_order
SET status = 3
WHERE id = 100 AND status = 1;      -- 直接用业务状态做条件
```

| 优点 | 缺点 |
|---|---|
| **只要 1 次 SQL**，不用先查 | 依赖"有明确的状态字段" |
| 语义更清晰（"从未支付改成已取消"） | 状态字段越多，条件越复杂 |

#### 我们怎么做

**主方案用 version 字段**（简历上写的就是这个，面试标准答案），**同时知道状态 CAS 更轻量**。

> 真实项目里，**订单状态变更这类"状态机"场景，用状态 CAS（写法 B）更常见也更高效**。
> version 字段更适合"任何字段都可能被并发改"的通用场景。

## 3. 第 1 步：表结构改造（version + active_flag）

### 3.1 为什么需要 `active_flag`

**先想清楚业务**：用户抢到券但忘记付款，订单 1 分钟后超时关闭。

> **他还能再买吗？**

| 答案 | 后果 |
|---|---|
| ❌ 不能（"抢到即算"） | 用户只是忘了付款，却永久失去资格 → **用户体验很差** |
| ✅ **能（主流电商做法）** | 需要解决唯一索引的冲突问题 |

**我们要的是"能再买"。** 但这里有个技术障碍：

```sql
UNIQUE KEY uk_user_voucher (user_id, voucher_id)
```

**这个唯一索引不看 `status`。** 只要 `(2001, 1)` 这一行还在（哪怕 status=3 已取消），就再也插不进第二条。

**两种错误做法：**

| 做法 | 结果 |
|---|---|
| 关单时 `SREM` 放用户出来，但不动唯一索引 | Lua 放行、DB 插入失败 → **库存不一致**（这是真实踩过的 bug） |
| 关单时不 `SREM` | 用户永久不能重买 → **业务不对** |

### 3.2 正确解法：`active_flag` + 唯一索引的 NULL 特性 ⭐

**核心技巧（记住这个，面试可讲）：**

> **MySQL 的唯一索引允许多个 `NULL` 值。**
> 因为 SQL 里 `NULL` 表示"未知"，两个 `NULL` 不相等 → 去重判断时会被跳过。

**利用这个特性，把索引扩成三列：**

```sql
UNIQUE KEY uk_user_voucher (user_id, voucher_id, active_flag)
```

| 订单状态 | `active_flag` | 占用唯一槽位？ |
|---|---|---|
| 未支付 / 已支付 | **`1`** | ✅ 占住 → **同一用户只能有 1 个有效订单** |
| 已取消 | **`NULL`** | ❌ 不占 → **可以有无穷多个取消记录** |

**推演一下：**

```sql
INSERT (2001, 1, 1);      -- ✅ 第一个有效订单
INSERT (2001, 1, 1);      -- ❌ 冲突！"一人一单"生效
INSERT (2001, 1, NULL);   -- ✅ 已取消的，不占位
INSERT (2001, 1, NULL);   -- ✅ 多个 NULL 不算重复
INSERT (2001, 1, NULL);   -- ✅ 允许很多条
```

**于是两件事同时成立：**

- ✅ **一人一单**：DB 层保证一个用户对一张券最多 1 个**有效**订单
- ✅ **可重新购买**：取消的记录不占位，用户可以再抢

### 3.3 执行 SQL

```sql
USE zhilan;

ALTER TABLE `voucher_order`
    -- ① 加乐观锁版本号
    ADD COLUMN `version` INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本号' AFTER `status`,
    -- ② 加有效标记
    ADD COLUMN `active_flag` TINYINT NULL DEFAULT 1 COMMENT '1=有效 NULL=已失效' AFTER `version`,
    -- ③ 重建唯一索引（原来的两列改成三列）
    DROP INDEX `uk_user_voucher`,
    ADD UNIQUE KEY `uk_user_voucher` (`user_id`, `voucher_id`, `active_flag`);

-- 确认字段
DESC voucher_order;

-- 确认索引有 3 列
SHOW INDEX FROM voucher_order WHERE Key_name = 'uk_user_voucher';
```

**`SHOW INDEX` 的输出应该有 3 行**（`Seq_in_index` 分别是 1、2、3）：

| Seq_in_index | Column_name |
|---|---|
| 1 | user_id |
| 2 | voucher_id |
| 3 | **active_flag** |

**如果只有 2 行，说明 `DROP INDEX` 没执行成功** —— 两个同名索引不能共存，检查一下。

### 3.4 同步更新 `sql/init.sql`

把建表语句改成（方便以后重建库）：

```sql
CREATE TABLE `voucher_order` (
    `id`          BIGINT   NOT NULL AUTO_INCREMENT COMMENT '主键',
    `user_id`     BIGINT   NOT NULL COMMENT '下单用户',
    `voucher_id`  BIGINT   NOT NULL COMMENT '优惠券id',
    `status`      TINYINT  NOT NULL DEFAULT 1 COMMENT '1未支付 2已支付 3已取消 4已退款',
    `version`     INT      NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
    `active_flag` TINYINT  NULL     DEFAULT 1 COMMENT '1=有效 NULL=已失效',
    `create_time` DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `pay_time`    DATETIME DEFAULT NULL COMMENT '支付时间',
    `update_time` DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_user_voucher` (`user_id`, `voucher_id`, `active_flag`),
    KEY `idx_voucher_id` (`voucher_id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '优惠券订单';
```

> **注意 `active_flag` 必须允许 `NULL`**（`TINYINT NULL`）。
> 如果写成 `NOT NULL`，多个已取消订单就无法共存 → 用户只能取消一次，第二次取消会失败。

## 4. 第 2 步：实体 + 乐观锁插件

### 4.1 VoucherOrder 加 version 和 active_flag

在 `entity/VoucherOrder.java` 里加：

```java
import com.baomidou.mybatisplus.annotation.FieldStrategy;
import com.baomidou.mybatisplus.annotation.Version;

    /** 有效标记常量：1 = 有效订单 */
    public static final int ACTIVE_FLAG_VALID = 1;

    /** 乐观锁版本号 */
    @Version
    private Integer version;

    /**
     * 有效标记：1=有效（未支付/已支付）  NULL=已失效（已取消）
     *
     * 用于唯一索引 uk_user_voucher(user_id, voucher_id, active_flag)：
     *   - 有效订单占住槽位 → 一人一单
     *   - 已取消订单为 NULL → 不占位，可以有多条 → 用户能重新购买
     *
     * ⚠️ updateStrategy = ALWAYS 必须加！
     *    默认的 NOT_NULL 策略会跳过 null 字段，导致无法把 active_flag 置空。
     */
    @TableField(updateStrategy = FieldStrategy.ALWAYS)
    private Integer activeFlag;
```

> ### ⚠️ `updateStrategy = FieldStrategy.ALWAYS` 是本项目最关键的注解之一
>
> **MyBatis-Plus 默认策略是 `NOT_NULL`**：字段值为 `null` 时**不拼进 UPDATE 语句**。
>
> **我们要把 `active_flag` 主动置成 `NULL`（关单时让出唯一槽位）。**
>
> | | 生成的 SQL | 结果 |
> |---|---|---|
> | 不加注解 | `UPDATE ... SET status=3, version=? WHERE ...`（**active_flag 消失**） | 仍是 `1` → 仍占槽位 → **用户还是不能重买** ❌ |
> | 加了注解 | `UPDATE ... SET status=3, active_flag=?, version=? WHERE ...`（`active_flag=null`） | 置为 `NULL` → 让出槽位 → **能重买** ✅ |
>
> **这个坑极其隐蔽**：代码看起来没问题，`updateById` 也返回 `true`，但 `active_flag` 就是没变。
> **验证方法**：看日志里的 UPDATE 语句，**`SET` 里有没有 `active_flag=?`**。

**`@Version` 是 MyBatis-Plus 的注解**，标记这个字段是乐观锁版本号。

> ### 🚨🚨 最容易踩的坑：`@Version` 有两个同名注解！
>
> | 包 | 用途 |
> |---|---|
> | **`com.baomidou.mybatisplus.annotation.Version`** | ✅ **我们要的是这个** |
> | `org.springframework.data.annotation.Version` | ❌ Spring Data 的（给 MongoDB/ES 用） |
>
> **IDEA 自动导入时会默认选第一个（Spring 的那个），导致乐观锁静默失效。**
>
> **失效的表现**（真实发生过）：
> ```sql
> -- 你以为是这样（有版本条件）
> UPDATE voucher_order SET status=3, version=version+1 WHERE id=125 AND version=0
>
> -- 实际是这样（没有任何乐观锁）
> UPDATE voucher_order SET status=3, version=? WHERE id=125
> ```
> **不报错、不警告，`updateById` 永远返回 true，乐观锁形同虚设。**
>
> #### ✅ 验证方法：看生成的 SQL
>
> 触发一次关单，在控制台日志里找 `updateById` 那条：
>
> | | SQL |
> |---|---|
> | ❌ 没生效 | `UPDATE ... SET ..., version=? WHERE id=?` |
> | ✅ 生效了 | `UPDATE ... SET ..., version=? WHERE id=? **AND version=?**` |
>
> **`import` 写对之后，`WHERE` 后面才会多出 `AND version=?`。**

### 4.2 注册乐观锁插件

修改 `config/MybatisPlusConfig.java`：

```java
package com.zhilan.zhilanserver.config;

import com.baomidou.mybatisplus.annotation.DbType;
import com.baomidou.mybatisplus.extension.plugins.MybatisPlusInterceptor;
import com.baomidou.mybatisplus.extension.plugins.inner.OptimisticLockerInnerInterceptor;
import com.baomidou.mybatisplus.extension.plugins.inner.PaginationInnerInterceptor;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class MybatisPlusConfig {

    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        // 分页插件
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
        // ⭐ 乐观锁插件（新增）
        interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());
        return interceptor;
    }
}
```

> **插件顺序有讲究**：乐观锁插件应该放在**分页插件之后**（MyBatis-Plus 官方推荐"分页最后加"其实说法不一，但本项目这两个插件互不影响，顺序无关紧要）。

### 4.3 乐观锁插件做了什么

**加了插件之后，你写的：**

```java
VoucherOrder order = getById(100L);   // status=1, version=0
order.setStatus(3);
updateById(order);
```

**MyBatis-Plus 实际执行的 SQL 变成：**

```sql
UPDATE voucher_order
SET status = 3, version = version + 1          -- ← 自动 +1
WHERE id = 100 AND version = 0;                -- ← 自动加版本条件
```

**你什么都不用写，插件自动帮你加上 `version` 条件。**

**如果影响行数 = 0** → 说明 version 已被别人改过（发生了冲突）→ `updateById` 返回 `false`。

### 4.4 ⚠️ 乐观锁的"使用前提"

**必须"先查后改"**，而且要用**查出来的那个实体对象**去更新：

```java
// ✅ 正确：先查
VoucherOrder order = getById(orderId);   // version 被填充
order.setStatus(3);
updateById(order);                        // 带上 version=0 的条件

// ❌ 错误：手动 new 一个，version 是 null
VoucherOrder order = new VoucherOrder();
order.setId(orderId);
order.setStatus(3);
updateById(order);        // version 为 null → 插件不生效 → 变成无条件的更新！

// ❌ 错误：忘记用查出来的 version
VoucherOrder order = getById(orderId);
VoucherOrder update = new VoucherOrder();
update.setId(orderId);
update.setStatus(3);
update.setVersion(order.getVersion());   // 也能行，但繁琐
updateById(update);
```

> **记住**：`@Version` 字段为 `null` 时，插件会**跳过**版本检查 —— 等于没有乐观锁。
> **这是最容易出错的地方。**

### 4.5 ⭐ 修改阶段 3 的 `createOrderFromMq`（必须做）

**因为表结构变了（加了 `active_flag`），阶段 3 写的消费者逻辑要跟着改两处。**

打开 `VoucherOrderServiceImpl.createOrderFromMq`，改：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void createOrderFromMq(SeckillOrderMessage message) {
    Long voucherId = message.getVoucherId();
    Long userId = message.getUserId();

    // ① 幂等检查：只查【有效订单】（⭐ 加了 active_flag 条件）
    long exists = count(new LambdaQueryWrapper<VoucherOrder>()
            .eq(VoucherOrder::getUserId, userId)
            .eq(VoucherOrder::getVoucherId, voucherId)
            .eq(VoucherOrder::getActiveFlag, VoucherOrder.ACTIVE_FLAG_VALID));
    if (exists > 0) {
        log.info("[MQ] 有效订单已存在，跳过处理（幂等）voucherId={}, userId={}", voucherId, userId);
        return;
    }

    // ② 扣数据库库存
    boolean deductSuccess = seckillVoucherService.update(
            new LambdaUpdateWrapper<SeckillVoucher>()
                    .setSql("stock = stock - 1")
                    .eq(SeckillVoucher::getId, voucherId)
                    .gt(SeckillVoucher::getStock, 0));

    if (!deductSuccess) {
        log.error("[MQ] 数据库库存不足，Redis 与 DB 不一致！voucherId={}", voucherId);
        throw new BusinessException(500, "数据库库存不足");
    }

    // ③ 创建订单（⭐ 标记为有效）
    VoucherOrder order = new VoucherOrder();
    order.setUserId(userId);
    order.setVoucherId(voucherId);
    order.setStatus(VoucherOrder.STATUS_UNPAID);
    order.setActiveFlag(VoucherOrder.ACTIVE_FLAG_VALID);   // ⭐ 新增
    save(order);
}
```

**两处改动，为什么必须：**

| 改动 | 不改会怎样 |
|---|---|
| ① 查重加 `active_flag = 1` | 用户**被关单后重买**时，会查到那张已取消的订单 → **跳过，不建新单** → 库存不一致 |
| ③ 创建时 `setActiveFlag(1)` | 新订单的 `active_flag` 是 `NULL` → **不占唯一槽位** → 一人一单失效，用户能买 N 次 |

> **第 ③ 条特别危险**：如果忘了设 `active_flag = 1`，虽然因为 DB 列有 `DEFAULT 1` 有可能兜住，
> 但一旦显式传了 `null`，就会插成 `NULL` → **唯一索引完全失效**。
> **显式设置，别依赖默认值。**

**验证**：抢一张券，看 INSERT 语句：

```
==>  Preparing: INSERT INTO voucher_order ( user_id, voucher_id, status, active_flag, create_time, update_time ) VALUES ( ?, ?, ?, ?, ?, ? )
==> Parameters: 2001(Long), 1(Long), 1(Integer), 1(Integer), ...
                                                    ↑ active_flag = 1
```

### 4.6 ⭐ 修改阶段 3 的 `getOrderByUser`（同样必须做）

**这个 bug 更隐蔽**：不报编译错，只在"用户有历史订单"时才炸。

打开 `VoucherOrderServiceImpl.getOrderByUser`，原来是：

```java
// ❌ 有 active_flag 之后，这会报错
public VoucherOrder getOrderByUser(Long voucherId, Long userId) {
    return getOne(new LambdaQueryWrapper<VoucherOrder>()
            .eq(VoucherOrder::getVoucherId, voucherId)
            .eq(VoucherOrder::getUserId, userId));
}
```

**问题**：用户"抢→取消→重抢"之后，`(userId, voucherId)` 会有**多条**记录。
MyBatis-Plus 的 `getOne(wrapper)` 内部是 `getOne(wrapper, true)`，**查到超过 1 条就抛 `TooManyResultsException`**：

```
org.apache.ibatis.exceptions.TooManyResultsException:
    Expected one result (or null) to be returned by selectOne(), but found: 3
```

**现象**：`GET /seckill/order/1` 返回 **500「系统繁忙」**（被全局异常处理器兜住，看不到真实原因）。

**改成：**

```java
@Override
public VoucherOrder getOrderByUser(Long voucherId, Long userId) {
    return getOne(new LambdaQueryWrapper<VoucherOrder>()
            .eq(VoucherOrder::getVoucherId, voucherId)
            .eq(VoucherOrder::getUserId, userId)
            .eq(VoucherOrder::getActiveFlag, VoucherOrder.ACTIVE_FLAG_VALID)   // ⭐ 只要有效订单
            .orderByDesc(VoucherOrder::getId)
            .last("LIMIT 1"));
}
```

**三处改动的作用：**

| 改动 | 作用 |
|---|---|
| `active_flag = 1` | 只看有效订单，历史已取消的不算 |
| `orderByDesc(id)` | 有多条有效订单时（理论上不该有）取最新的 |
| `LIMIT 1` | **物理上保证只返回 1 条，彻底杜绝 `TooManyResultsException`** |

> **`LIMIT 1` 是"防御性"写法**：正常情况唯一索引保证只有 1 条 `active_flag=1`，
> 但加上它成本为零，且能避免"数据脏了导致接口 500"。

### 4.7 本阶段要回头改的 3 处（汇总）

| # | 方法 | 改什么 |
|---|---|---|
| 1 | `createOrderFromMq` | 查重加 `active_flag=1`；创建时 `setActiveFlag(1)` |
| 2 | `getOrderByUser` | 加 `active_flag=1` + `LIMIT 1` |
| 3 | `closeOrder` | 加 `setActiveFlag(null)`；恢复 Redis `SREM`（见第 4 步） |

**这三处不改完，`active_flag` 方案就是半成品。**

### 5.3 支付实现

在 `VoucherOrderServiceImpl` 里加：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public boolean payOrder(Long orderId, Long userId) {
    // ① 先查（必须！乐观锁要求先拿到当前 version）
    VoucherOrder order = getById(orderId);
    if (order == null) {
        throw new BusinessException(404, "订单不存在");
    }
    if (!order.getUserId().equals(userId)) {
        throw new BusinessException(403, "无权操作此订单");
    }
    if (order.getStatus() == VoucherOrder.STATUS_PAID) {
        throw new BusinessException(400, "订单已支付，请勿重复支付");
    }
    if (order.getStatus() == VoucherOrder.STATUS_CANCELED) {
        throw new BusinessException(400, "订单已关闭，无法支付");
    }

    // ② 乐观锁更新（插件自动加 version 条件）
    order.setStatus(VoucherOrder.STATUS_PAID);
    order.setPayTime(LocalDateTime.now());
    boolean success = updateById(order);

    if (!success) {
        // version 不匹配 → 被人改过了（可能是定时任务刚关单）
        log.warn("[支付] 乐观锁冲突，orderId={}", orderId);

        // ⚠️ 必须用「当前读」：SELECT ... FOR UPDATE
        //    REPEATABLE READ 下，普通 SELECT 读的是事务开始时的快照，
        //    看不到别的线程已提交的新状态 → 下面的分支判断会全部失效！
        VoucherOrder latest = getOne(new LambdaQueryWrapper<VoucherOrder>()
                .eq(VoucherOrder::getId, orderId)
                .last("FOR UPDATE"));

        if (latest != null && latest.getStatus() == VoucherOrder.STATUS_CANCELED) {
            throw new BusinessException(400, "订单已超时关闭，无法支付");
        }
        if (latest != null && latest.getStatus() == VoucherOrder.STATUS_PAID) {
            throw new BusinessException(400, "订单已支付");
        }
        throw new BusinessException(409, "订单状态已变更，请刷新后重试");
    }

    log.info("[支付] 订单 {} 支付成功 userId={}", orderId, userId);
    return true;
}
```

> ### 🐛 这里有个真实踩到的 bug（必看）
>
> **最初写的是 `getById(orderId)` 重查，结果并发测试时发现：**
>
> ```
> >>> 关单: 成功
> [支付] 乐观锁冲突，orderId=145
> >>> 支付: 失败 - 订单状态已变更，请刷新后重试     ← 走的是 409 兜底分支！
> ```
>
> **但数据库里订单明明是 `status=3`（已取消）**，按代码应该抛「订单已超时关闭」。
>
> #### 根因：MySQL 的 REPEATABLE READ 快照
>
> **InnoDB 默认隔离级别是 `REPEATABLE READ`：事务里第一次 SELECT 会建立一致性快照，
> 之后该事务内所有普通 SELECT 都读这个快照 —— 即使别人已经提交了新数据。**
>
> ```
> 事务开始
>   ├─ ① getById(145)      → 建快照：status=1, version=0
>   ├─ ② 状态检查           → 快照：status=1（未支付，通过）
>   ├─ ③ updateById(...)   → 【当前读】看到最新：version=1 → Updates: 0 ❌
>   └─ ④ getById(145) 重查  → 【仍是快照】status=1 ！ ❌❌❌
> ```
>
> | 操作 | 读什么 |
> |---|---|
> | **普通 SELECT** | **快照**（事务开始时的视图） |
> | **UPDATE / SELECT ... FOR UPDATE** | **当前读**（最新已提交数据） |
>
> **所以第 ④ 步拿到的是过期的 `status=1`** → 三个分支全不命中 → 落到 409 兜底。
>
> #### 修复：把重查改成 `SELECT ... FOR UPDATE`
>
> ```java
> VoucherOrder latest = getOne(new LambdaQueryWrapper<VoucherOrder>()
>         .eq(VoucherOrder::getId, orderId)
>         .last("FOR UPDATE"));
> ```
>
> **改完就能正确提示「订单已超时关闭，无法支付」。**
>
> #### 为什么这个 bug 只有并发测试能发现？
>
> | 测试方式 | 结果 |
> |---|---|
> | **顺序测试**（先关单再支付） | `getById` 读到 status=3 → **走早退分支** → 提示正确 → **测不出问题** |
> | **并发测试**（同时读，关单先提交） | 走到冲突分支 → 快照导致判断失效 → **bug 暴露** |
>
> **这就是并发测试的真正价值：它暴露的不是"你已知逻辑对不对"，而是"你想不到的时序带来的问题"。**

### 5.4 逐块讲解

#### ① 先查、再判断、最后改

**这不是多余**，而是乐观锁的**必要步骤**：

```java
VoucherOrder order = getById(orderId);   // ← 拿到 version
...
boolean success = updateById(order);      // ← 插件用这个 version 做条件
```

**跳过查询直接 `new VoucherOrder()` 会破坏乐观锁**（version 为 null → 插件不生效）。

#### ② `updateById` 返回 false 的含义

**这是整个乐观锁的"结果信号"：**

| 返回值 | 含义 |
|---|---|
| `true` | 更新成功，我是"赢家" |
| `false` | 影响行数 0，说明 `WHERE ... AND version = ?` 没匹配上 → 别人改过了 |

**注意**：`false` **不是异常**，是"正常业务结果"（有冲突）。

#### ③ 为什么冲突后要重新查一次（以及为什么要用 `FOR UPDATE`）

```java
if (!success) {
    // ⚠️ 必须用当前读，不能用普通 SELECT
    VoucherOrder latest = getOne(new LambdaQueryWrapper<VoucherOrder>()
            .eq(VoucherOrder::getId, orderId)
            .last("FOR UPDATE"));

    if (latest.getStatus() == CANCELED) → "订单已超时关闭"     ← 精确提示
    if (latest.getStatus() == PAID)     → "订单已支付"        ← 精确提示
    else                                → "状态已变更"        ← 兜底
}
```

**好处**：用户看到的不再是"系统繁忙"，而是**"订单已超时关闭"** —— 能指导下一步动作。

**这就是"错误信息要有用"的实践。**

> **⚠️ 但必须用 `FOR UPDATE`！**
>
> 用普通的 `getById()` 会读到**事务快照**（旧数据），三分支全部失效 → 永远落到 409 兜底。
> 详细分析和真实 bug 复现见 5.3 节的说明。

#### ④ `@Transactional(rollbackFor = Exception.class)` 的必要性

支付只改了 1 张表，理论上不需要事务。但**加上它**有好处：
- 以后如果加了"支付成功 → 发消息通知""记录流水"等操作，自动纳入事务
- `rollbackFor = Exception.class` 保证**受检异常也回滚**（Spring 默认只回滚 RuntimeException）

> **但加了事务就要注意事务快照问题**（见 ③）—— 事务内想看到"别人刚提交的数据"，必须用当前读。

## 6. 第 4 步：关单 + 回补库存

### 6.1 核心逻辑：只有"抢到关单权"的人才回补库存

这是本阶段**最关键的一段代码**：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public boolean closeOrder(Long orderId) {
    // ① 先查（拿 version）
    VoucherOrder order = getById(orderId);
    if (order == null) {
        return false;
    }
    // ② 快速判断：不是未支付状态就不用管
    if (order.getStatus() != VoucherOrder.STATUS_UNPAID) {
        return false;
    }

    // ③ 乐观锁更新状态：1(未支付) → 3(已取消)，同时【让出唯一索引槽位】
    order.setStatus(VoucherOrder.STATUS_CANCELED);
    order.setActiveFlag(null);        // ⭐ 关键：置 NULL，允许用户重新购买
    boolean success = updateById(order);

    if (!success) {
        // 没抢到！说明：
        //   - 用户刚好支付了（status 变 2，version 变了）
        //   - 或者别的线程已经关过了
        // → 什么都不做，绝不能回补库存！
        log.info("[关单] 乐观锁冲突，跳过 orderId={}", orderId);
        return false;
    }

    // ④ 到这里说明我成功抢到了关单权 → 才回补库存
    Long voucherId = order.getVoucherId();
    Long userId = order.getUserId();

    // ④-1 回补数据库库存
    seckillVoucherService.update(
            new LambdaUpdateWrapper<SeckillVoucher>()
                    .setSql("stock = stock + 1")
                    .eq(SeckillVoucher::getId, voucherId));

    // ④-2 回补 Redis 库存
    stringRedisTemplate.opsForValue()
            .increment(RedisKeyConstants.SECKILL_STOCK_KEY + voucherId);

    // ④-3 把用户从"已下单集合"移除 → 重获购买资格
    stringRedisTemplate.opsForSet()
            .remove(RedisKeyConstants.SECKILL_ORDER_KEY + voucherId, String.valueOf(userId));

    log.info("[关单] 订单 {} 已关闭，库存已回补，用户可重新购买 voucherId={}, userId={}",
            orderId, voucherId, userId);
    return true;
}
```

> #### 关单要做的「三件事」
>
> | # | 动作 | 漏了会怎样 |
> |---|---|---|
> | ① | `setActiveFlag(null)` | **用户永久不能重买**（旧订单还占着唯一索引） |
> | ② | DB stock +1 / Redis stock +1 | 券凭空消失 |
> | ③ | Redis `SREM` 用户 | Lua 层拒绝，用户抢不了 |
>
> **三件事必须一起做**，少一件就会出现"某处认为能买、某处认为不能买"的错位。

### 6.2 ⚠️ 逐块讲解：为什么顺序不能变

#### 「先抢关单权，再回补库存」是铁律

**看这个错误写法：**

```java
// ❌ 绝对错误：先回补库存，再改状态
stringRedisTemplate.opsForValue().increment(stockKey);       // 库存 +1
boolean success = updateById(order);                          // 再改状态
if (!success) { /* 冲突了 */ }                                // 但库存已经加了！
```

**灾难推演：**

```
线程 A（支付）                线程 B（关单，错误写法）
──────────────────────────────────────────────────────
UPDATE status=2 ✅

                             Redis 库存 +1        ← 先加了
                             UPDATE status=3
                             → 0 行（支付赢了）
                             → 但库存已经 +1 了！
──────────────────────────────────────────────────────
最终：订单已支付（不回补），但库存却 +1 → 超卖！💀
```

**正确顺序保证**：**只有"确定关单成功"之后才回补。**

#### ⚠️ 关单后用户必须能"重新购买"—— 四处必须对齐

**业务前提**：用户只是**忘记付款**，不是有意放弃。**剥夺他重新购买的资格不合理。**

阶段 3 的 Lua 脚本会检查 `seckill:order:{voucherId}` 集合：

```lua
if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then
    return 1        -- 已下单，拒绝
end
```

**"一人一单"这个规则，在系统里出现在 4 个地方，必须全部对齐：**

| # | 位置 | 关单后应该 |
|---|---|---|
| ① | Redis `seckill:order:{id}` 集合 | **SREM**（用户重获资格） |
| ② | 消费者的 `count` 查重 | **只查 `active_flag = 1`**（忽略已取消的） |
| ③ | 唯一索引 `uk_user_voucher` | **`active_flag` 置 NULL**（让出槽位） |
| ④ | `closeOrder` 的更新 | 同时改 `status=3` 和 `active_flag=NULL` |

**任何一处没对齐，就会出 bug。**

#### 🐛 这是真实踩到的 bug（不对齐的后果）

**当时的代码**：① 做了 SREM，但 ②③ 没改。

```
[关单] 订单 125 已关闭，库存已回补           ← 用户被放出来了
[MQ] 已发送秒杀订单消息 voucherId=1, userId=2001
[MQ] 收到订单消息 voucherId=1, userId=2001
SELECT COUNT(*) ... WHERE (user_id = ? AND voucher_id = ?)  → 2001, 1
<== Total: 1                                 ← 查到那张【已取消】的订单
[MQ] 订单已存在，跳过处理（幂等）              ← 跳过，没有建新订单！
```

**结果**：Lua 放行了（Redis 库存 -1），但消费者跳过了（DB 库存没扣、订单没建）
→ **Redis 和 DB 库存永久不一致，券凭空消失。**

**矛盾点：**

| 位置 | 行为 |
|---|---|
| `closeOrder` 的 `SREM` | **允许**重买 |
| 唯一索引（两列，不看 status） | **禁止**（已取消的订单还占着索引） |
| 消费者的 `count` 查重（不过滤状态） | **禁止** |

**④ 和其他三个方向相反 → 必然出问题。**

#### ✅ 本项目的解法：`active_flag` 让四处一致

| 位置 | 关单后 |
|---|---|
| ① `SREM` | 用户不在集合里 → Lua 放行 ✅ |
| ② `count ... and active_flag = 1` | 查不到有效订单 → 建新单 ✅ |
| ③ `active_flag = NULL` | 旧订单让出唯一槽位 → 新单能插入 ✅ |
| ④ `updateById` 同时改两个字段 | 一次事务内完成 ✅ |

**四者一致，用户能顺畅地重新购买。**

#### 为什么要保留已取消的订单记录

**订单被"关闭"，不是"删除"。** 记录要留着：
- 用户能查历史订单
- 客服能查证（"我确实抢过但过期了"）
- 审计需要

**只是 `status` 从 1 变成 3，`active_flag` 从 1 变成 NULL。**

**所以一个用户对同一张券可能有多条订单记录：**

```
id=127, status=3, active_flag=NULL    ← 第一次抢，超时关闭
id=131, status=1, active_flag=1       ← 重新抢，有效
```

**但永远只有 1 条 `active_flag=1` 的** —— 这就是"一人一单"的真正含义：
**同时只能有一个有效订单**，而不是"一辈子只能买一次"。

#### 为什么不回滚 DB 的订单记录

**订单被"关闭"，不是"删除"。** 记录要留着：
- 用户能查历史订单
- 客服能查证
- 审计需要

**只是 `status` 从 1 变成 3。**

### 6.3 `listOverdueOrders` 实现

```java
@Override
public List<VoucherOrder> listOverdueOrders(LocalDateTime deadline, int limit) {
    return list(new LambdaQueryWrapper<VoucherOrder>()
            .eq(VoucherOrder::getStatus, VoucherOrder.STATUS_UNPAID)
            .lt(VoucherOrder::getCreateTime, deadline)
            .orderByAsc(VoucherOrder::getCreateTime)
            .last("LIMIT " + limit));
}
```

**讲解：**

| 条件 | 作用 |
|---|---|
| `status = 1` | 只看未支付的 |
| `create_time < deadline` | 只看超时的 |
| `order by create_time asc` | **先关最早的**（公平，也避免一直处理同几条） |
| `LIMIT 100` | **防止一次查太多**（如果积压 10 万个订单，一次全查会 OOM） |

> ⚠️ **`.last("LIMIT " + limit)` 的注意点**：这里 `limit` 是 `int`（不是用户输入的字符串），所以没有 SQL 注入风险。
> **但如果是用户传入的字符串，绝对不能这样拼。**

### 7.3 定时任务类

新建 `task/OrderTimeoutTask.java`：

```java
package com.zhilan.zhilanserver.task;

import com.zhilan.zhilanserver.entity.VoucherOrder;
import com.zhilan.zhilanserver.service.VoucherOrderService;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import java.time.LocalDateTime;
import java.util.List;

/**
 * 订单超时自动关闭任务
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class OrderTimeoutTask {

    private final VoucherOrderService voucherOrderService;

    /** 超时时长（分钟），从配置读取，默认 15 */
    @Value("${zhilan.order.timeout-minutes:15}")
    private int timeoutMinutes;

    /**
     * 每分钟的第 0 秒执行一次
     * cron 表达式：秒 分 时 日 月 周
     */
    @Scheduled(cron = "0 */1 * * * ?")
    public void closeTimeoutOrders() {
        LocalDateTime deadline = LocalDateTime.now().minusMinutes(timeoutMinutes);

        List<VoucherOrder> overdue = voucherOrderService.listOverdueOrders(deadline, 100);
        if (overdue.isEmpty()) {
            return;         // 没有超时订单，直接返回（避免刷日志）
        }

        log.info("[定时关单] 发现 {} 个超时订单（超时阈值 {} 分钟）", overdue.size(), timeoutMinutes);

        int successCount = 0;
        for (VoucherOrder order : overdue) {
            try {
                // ⭐ 每单单独处理：一单失败不影响其他单
                if (voucherOrderService.closeOrder(order.getId())) {
                    successCount++;
                }
            } catch (Exception e) {
                log.error("[定时关单] 关闭订单 {} 失败", order.getId(), e);
            }
        }

        log.info("[定时关单] 本轮处理完成：成功 {}/{}", successCount, overdue.size());
    }
}
```

### 7.4 讲解

#### ① cron 表达式怎么读

```
0 */1 * * * ?
│  │  │ │ │ │
│  │  │ │ │ └─ 星期（? = 不指定）
│  │  │ │ └─── 月
│  │  │ └───── 日
│  │  └─────── 时
│  └────────── 分（*/1 = 每 1 分钟）
└───────────── 秒
```

**常用 cron 速查：**

| 表达式 | 含义 |
|---|---|
| `0 */1 * * * ?` | **每分钟**（本项目） |
| `0 0 */1 * * ?` | 每小时整点 |
| `0 0 2 * * ?` | 每天凌晨 2 点 |
| `0 */5 * * * ?` | 每 5 分钟 |
| `0 0 0 * * ?` | 每天 0 点 |

> **秒级测试用** `0/10 * * * * ?`（每 10 秒一次），调试时很方便。

#### ② 为什么每单要 `try-catch`

```java
for (VoucherOrder order : overdue) {
    try {
        voucherOrderService.closeOrder(order.getId());
    } catch (Exception e) {
        log.error(...);        // 记录，继续处理下一单
    }
}
```

**如果不用 try-catch**：第 3 单抛异常 → 整个循环中断 → **第 4~100 单都不会被处理**。

**批量处理铁律**：**单个失败不能影响整体。**

#### ③ 为什么每单独立事务

`closeOrder` 上有 `@Transactional`，而且是**从 Task 类（另一个类）调用的** → 走 Spring 代理 → **事务生效**。

**所以每一单是一个独立事务：**
- 单 1 成功 → 提交
- 单 2 失败 → 回滚（但单 1 已经提交，不受影响）

**这又是"跨类调用事务才生效"的一次应用。**

#### ④ 为什么要 `LIMIT 100`

**假设积压了 10 万个超时订单：**

```java
// ❌ 危险写法
List<VoucherOrder> all = list(...);   // 一次查出 10 万条 → OOM
```

**用 LIMIT 分批处理**：每分钟处理 100 个，10 万个需要 1000 分钟（约 17 小时）。

**如果积压量很大，应该**：
- 缩短执行间隔（比如每 10 秒）
- 或增大 `LIMIT`
- 或用多线程处理（但要注意并发安全）

**我们项目数据量小，LIMIT 100 足够。**

### 9.2 测试代码（自动准备数据版）⭐

**这个版本不需要手工抢券、不需要改常量，跑一次自动准备一次数据，可以连续跑 10 次。**

新建 `src/test/java/com/zhilan/zhilanserver/OrderConcurrencyTest.java`：

```java
package com.zhilan.zhilanserver;

import com.zhilan.zhilanserver.entity.SeckillVoucher;
import com.zhilan.zhilanserver.entity.VoucherOrder;
import com.zhilan.zhilanserver.service.SeckillVoucherService;
import com.zhilan.zhilanserver.service.VoucherOrderService;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.data.redis.core.StringRedisTemplate;

import java.util.Objects;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

/**
 * 支付 vs 关单 并发冲突测试（自动准备数据版）
 *
 * 每次运行会：
 *   1. 用一个新的 userId（不重复）
 *   2. 把 DB 库存同步到 Redis，清空已下单集合
 *   3. 走完整链路抢一张券（Lua → MQ → 消费者）
 *   4. 同时发起「支付」和「关单」
 *   5. 自动校验结果是否符合预期
 *
 * ✅ 不需要改常量，可以直接重复运行 10 次
 * ⚠️ 前提：数据库里 seckill_voucher.id=1 的 stock 必须 > 0
 */
@SpringBootTest
class OrderConcurrencyTest {

    @Autowired
    private VoucherOrderService voucherOrderService;
    @Autowired
    private SeckillVoucherService seckillVoucherService;
    @Autowired
    private StringRedisTemplate stringRedisTemplate;

    private static final Long VOUCHER_ID = 1L;
    private static final String STOCK_KEY = "seckill:stock:" + VOUCHER_ID;
    private static final String ORDER_SET_KEY = "seckill:order:" + VOUCHER_ID;

    @Test
    void testPayVsClose() throws Exception {
        // ==================== ① 自动准备数据 ====================

        // 每次用不同 userId，避免和之前测试的订单冲突
        long userId = 100000 + System.currentTimeMillis() % 100000;

        // 检查数据库库存
        SeckillVoucher voucher = seckillVoucherService.getById(VOUCHER_ID);
        if (voucher == null) {
            throw new IllegalStateException("优惠券 " + VOUCHER_ID + " 不存在");
        }
        if (voucher.getStock() == null || voucher.getStock() <= 0) {
            throw new IllegalStateException(
                    "数据库库存为 0，无法测试。请先执行：\n" +
                    "  USE zhilan;\n" +
                    "  UPDATE seckill_voucher SET stock = 10 WHERE id = 1;");
        }

        // 把库存同步到 Redis（保证 Redis 与 DB 一致），并清空已下单集合
        stringRedisTemplate.opsForValue().set(STOCK_KEY, String.valueOf(voucher.getStock()));
        stringRedisTemplate.delete(ORDER_SET_KEY);

        // 走完整链路抢券（Lua → MQ → 消费者异步建单）
        voucherOrderService.seckillVoucher(VOUCHER_ID, userId);

        // 等消费者把订单建好（异步，必须轮询等待）
        VoucherOrder order = null;
        for (int i = 0; i < 30; i++) {
            Thread.sleep(100);
            order = voucherOrderService.getOrderByUser(VOUCHER_ID, userId);
            if (order != null) {
                break;
            }
        }
        if (order == null) {
            throw new IllegalStateException("准备失败：等待 3 秒订单仍未创建，检查 MQ 消费者是否正常");
        }

        Long orderId = order.getId();
        String stockBefore = stringRedisTemplate.opsForValue().get(STOCK_KEY);

        System.out.println("================ 准备完成 ================");
        System.out.println("userId       = " + userId);
        System.out.println("orderId      = " + orderId);
        System.out.println("status       = " + order.getStatus() + "  (1未支付)");
        System.out.println("activeFlag   = " + order.getActiveFlag() + "  (1有效)");
        System.out.println("version      = " + order.getVersion());
        System.out.println("关单前 Redis 库存 = " + stockBefore);
        System.out.println("=========================================");

        // ==================== ② 并发触发 ====================

        CountDownLatch startGun = new CountDownLatch(1);   // 发令枪
        CountDownLatch done = new CountDownLatch(2);       // 两个线程都结束
        ExecutorService pool = Executors.newFixedThreadPool(2);

        // 线程 1：支付
        pool.submit(() -> {
            try {
                startGun.await();
                voucherOrderService.payOrder(orderId, userId);
                System.out.println(">>> 支付: 成功");
            } catch (Exception e) {
                System.out.println(">>> 支付: 失败 - " + e.getMessage());
            } finally {
                done.countDown();
            }
        });

        // 线程 2：关单
        pool.submit(() -> {
            try {
                startGun.await();
                boolean ok = voucherOrderService.closeOrder(orderId);
                System.out.println(">>> 关单: " + (ok ? "成功" : "失败（未抢到）"));
            } catch (Exception e) {
                System.out.println(">>> 关单: 异常 - " + e.getMessage());
            } finally {
                done.countDown();
            }
        });

        startGun.countDown();               // 🔫 两个线程同时起跑
        done.await(10, TimeUnit.SECONDS);
        pool.shutdown();

        // ==================== ③ 读取最终状态 ====================

        VoucherOrder finalOrder = voucherOrderService.getById(orderId);
        String stockAfter = stringRedisTemplate.opsForValue().get(STOCK_KEY);
        Boolean inSet = stringRedisTemplate.opsForSet()
                .isMember(ORDER_SET_KEY, String.valueOf(userId));

        System.out.println("================ 最终状态 ================");
        System.out.println("status       = " + finalOrder.getStatus() + "  (2已支付 / 3已取消)");
        System.out.println("activeFlag   = " + finalOrder.getActiveFlag() + "  (1有效 / null已取消)");
        System.out.println("version      = " + finalOrder.getVersion() + "  (改过状态就是 1)");
        System.out.println("Redis 库存   = " + stockBefore + " → " + stockAfter);
        System.out.println("用户还在集合 = " + inSet);
        System.out.println("=========================================");

        // ==================== ④ 自动校验 ====================

        int status = finalOrder.getStatus();

        if (status == VoucherOrder.STATUS_PAID) {
            // ---------- 结果 A：支付赢了 ----------
            // ⚠️ 用 Objects.equals 而不是 stockBefore.equals()：
            //    Redis get 可能返回 null，直接 .equals() 会 NPE
            if (!Objects.equals(stockBefore, stockAfter)) {
                throw new AssertionError("❌【超卖】支付成功但库存被回补了！"
                        + stockBefore + " → " + stockAfter);
            }
            if (!Integer.valueOf(VoucherOrder.ACTIVE_FLAG_VALID)
                    .equals(finalOrder.getActiveFlag())) {
                throw new AssertionError("❌ 支付成功但 active_flag 不是 1，实际 = "
                        + finalOrder.getActiveFlag());
            }
            if (!Boolean.TRUE.equals(inSet)) {
                throw new AssertionError("❌ 支付成功但用户被移出了已下单集合");
            }
            System.out.println("✅ 结果正常：支付赢了 → 库存不变、active_flag=1、用户在集合里");

        } else if (status == VoucherOrder.STATUS_CANCELED) {
            // ---------- 结果 B：关单赢了 ----------
            // 先防 null，否则 Integer.parseInt(null) 会抛含义模糊的 NumberFormatException
            if (stockBefore == null || stockAfter == null) {
                throw new AssertionError("❌ 库存 key 不存在：" + STOCK_KEY
                        + "（before=" + stockBefore + ", after=" + stockAfter + "）");
            }
            int before = Integer.parseInt(stockBefore);
            int after = Integer.parseInt(stockAfter);
            if (after != before + 1) {
                throw new AssertionError("❌【少卖】关单成功但库存没 +1："
                        + before + " → " + after);
            }
            if (finalOrder.getActiveFlag() != null) {
                throw new AssertionError("❌ 关单成功但 active_flag 不是 NULL，实际 = "
                        + finalOrder.getActiveFlag() + "（用户将无法重新购买）");
            }
            if (!Boolean.FALSE.equals(inSet)) {
                throw new AssertionError("❌ 关单成功但用户还在已下单集合里");
            }
            System.out.println("✅ 结果正常：关单赢了 → 库存 +1、active_flag=NULL、用户被移除");

        } else {
            // ---------- 结果 C：两个都没成功（异常情况） ----------
            throw new AssertionError("❌ 订单停留在 status=" + status
                    + "，说明支付和关单都没生效，检查日志");
        }
    }
}
```

> ### 💡 关于断言里的 `!`
>
> **`if (!期望条件) throw` 是断言的标准写法：**
>
> ```java
> // 结果 A 的期望：库存不变
> 期望 = stockBefore.equals(stockAfter)
> 
> // 反过来就是错误情况
> if (!期望) { throw ... }
> ```
>
> | 情况 | 期望值 | `!期望` | 结果 |
> |---|---|---|---|
> | 库存没变（正确） | `true` | `false` | 不抛 ✅ |
> | 库存变了（超卖） | `false` | `true` | 抛异常 ✅ |
>
> **去掉 `!` 就完全反了**：正常情况反而报错。
>
> ### ⚠️ 为什么必须用 `Objects.equals` 而不是 `stockBefore.equals`
>
> `stringRedisTemplate.opsForValue().get(key)` 的返回类型是 **`@Nullable String`** —— key 不存在时返回 `null`。
>
> ```java
> stockBefore.equals(stockAfter)          // ❌ stockBefore 为 null → NPE
> Objects.equals(stockBefore, stockAfter) // ✅ null 安全
> ```
>
> **`Objects.equals` 的规则：**
>
> | a | b | 结果 |
> |---|---|---|
> | null | null | `true` |
> | null | "9" | `false` |
> | "9" | "9" | `true` |
>
> **测试代码里 NPE 比"断言失败"难查得多** —— 你只看到 NPE，不知道是哪一步出错。
> **需要 import：`import java.util.Objects;`**

**这个版本比手工版好在哪：**

| | 手工版 | **自动版** |
|---|---|---|
| 准备数据 | 抢券 + 手改常量 | **自动** |
| 等 MQ 建单 | 自己估时间 | **轮询等待**（最多 3 秒） |
| 用户 id | 固定，跑多次会冲突 | **每次新的** |
| 结果判断 | 人眼看 | **代码断言，错就抛异常** |
| 连跑 10 次 | 要改 10 次常量 | **直接连跑** ✅ |

> **`version` 应该变成 1**：因为状态被改过一次（支付 1→2 或关单 1→3）。
> 如果 `version` 还是 0，说明乐观锁没生效 —— 但那样两个线程可能都"成功"，走到结果 C 分支。

### 9.4 连跑 10 次

**因为测试是自动准备的，你可以直接点 ▶ 跑第二次、第三次……每次都是新用户、新订单。**

**建议连跑 10 次**，原因是：

> **并发 bug 是概率性的。** 两个线程同时到达的时间窗口可能只有零点几毫秒，
> 跑 1 次通过完全不能说明问题，**跑 10 次都通过才有说服力。**

**IDEA 连跑技巧**：点测试方法左边的 ▶ → 每次都会重新执行整个方法（包括准备数据）。

**统计一下结果分布**：

| 结果 | 次数 |
|---|---|
| ✅ 支付赢了 | ? |
| ✅ 关单赢了 | ? |
| ❌ 失败 | **必须是 0** |

> **只要出现 1 次 ❌，就说明有并发漏洞，必须查。**

#### ⚠️ 实测发现：大概率 10 次全是"支付赢"（这很正常）

**真实测试结果**：连跑 10 次，**全部是"支付赢"**。交换 `pool.submit` 的顺序后，**依然是"支付赢"**。

**原因是：**

1. **`payOrder` 的代码路径更短** —— UPDATE 之后只打一行日志就返回（事务立即提交）
2. **`closeOrder` 的 UPDATE 之后还要回补 DB 库存 + 两次 Redis 操作**，事务持有行锁时间长得多
3. **更根本的：两个线程醒来后要先各自做一次 `selectById`（DB 往返），这中间的交错由 JVM/OS 调度决定，`submit` 顺序控制不了**

**所以「靠交换提交顺序来切换胜负」是不靠谱的。**

> **这本身就是并发测试的重要认知**：
> 你能"同时开始"，但**控制不了之后的交错顺序**。
> 专业工具（`jcstress`、字节码插桩、故障注入）才能精确控制，普通单测做不到。

#### ✅ 核心结论已经证明了，不必强求两种结果

**10 次"支付赢"已经证明了这一阶段最关键的 4 件事：**

| 已证明 | 证据 |
|---|---|
| 两个线程**同时读到** version=0 | 两条 `selectById` 在同一毫秒 |
| 乐观锁**真的拦截**了第二个 | `Updates: 0` + `[关单] 乐观锁冲突` |
| **没有双成功** | 10/10 次 |
| **失败方零副作用** | 支付赢的 10 次里，库存**一次都没**被回补 |

**"关单赢"的副作用**（库存 +1、`active_flag=NULL`、Redis SREM）已在 8.2 节的**顺序测试**里验证过。

#### 想强制"关单赢"：给支付线程加 2ms 延迟

**在支付线程的 `await()` 后加一句：**

```java
// 线程 2：支付（延迟 2ms，让关单先执行 UPDATE）
pool.submit(() -> {
    try {
        startGun.await();
        Thread.sleep(2);          // ⭐ 让关单先走一步
        voucherOrderService.payOrder(orderId, userId);
        ...
```

**时间线推演：**

```
t=0ms    关单: selectById → version=0
t=0ms    关单: UPDATE     → 拿到行锁，version 变 1（未提交）
t=0~5ms  关单: 回补 DB 库存 + Redis（行锁一直持有）

t=2ms    支付: selectById → 读已提交快照 → 仍是 version=0 ✅
t=2ms+   支付: UPDATE     → 阻塞等行锁

t≈5ms    关单提交 → 释放行锁
t≈5ms    支付: UPDATE 继续 → WHERE version=0 不匹配 → Updates: 0
         → 走乐观锁冲突分支 → 重查 → status=3 → "订单已超时关闭" ✅
```

#### ⚠️ 判断走的是哪个分支（关键）

**`payOrder` 有两条"订单已关闭"的路径，输出不同：**

| 分支 | 输出 | 说明 |
|---|---|---|
| **① 早退** | 直接 `"订单已关闭，无法支付"` | `getById` 时 status 已是 3 → **没测到冲突** |
| **② 乐观锁冲突** | **先打 `[支付] 乐观锁冲突，orderId=xxx`**，再 `"订单已超时关闭，无法支付"` | ✅ **这才是我们要的** |

**验证标准：日志里有没有 `[支付] 乐观锁冲突` 这一行。**

| sleep 值 | 结果 |
|---|---|
| `0` | 支付总赢 |
| **`2`** | ✅ 理想：关单赢 + 走冲突分支 |
| `10` | 关单赢，但支付走**早退分支**（已变成顺序执行）→ 调小 |

**从 `2` 开始试，最多调 3~4 次。**

```sql
SELECT id, status, version, update_time FROM voucher_order ORDER BY id DESC LIMIT 10;
```

**每次状态变更，version 都会 +1。看到 version 没变而 status 变了 → 乐观锁没生效。**

**④ 确认定时任务真的在跑**

在任务开头加一行日志：

```java
log.debug("[定时关单] 开始扫描，deadline={}", deadline);
```

**如果这行都不打印 → `@EnableScheduling` 的问题。**

## 附录 A：本阶段核心知识速查

| 概念 | 一句话 |
|---|---|
| **超时关单** | 未支付订单占着库存，超时后自动关闭并回补 |
| **并发冲突** | 支付和关单同时改一个订单，可能互相覆盖 |
| **乐观锁** | 更新时带上旧状态作为条件，用影响行数判断是否抢到 |
| **`@Version`** | MyBatis-Plus 自动加 `AND version = ?` 和 `SET version = version + 1` |
| **`@Version` 的坑** | 必须 import `com.baomidou...`，导成 Spring Data 的会静默失效 |
| **必须"先查后改"** | version 为 null 时插件失效 |
| **先抢权，后回补** | `updateById` 成功才回补库存，顺序绝不能反 |
| **关单三件事** | `active_flag=NULL`、DB stock+1、Redis stock+1、Redis SREM 用户 |
| **`active_flag` 技巧** | MySQL 唯一索引允许多个 NULL → 已取消订单不占位，用户可重买 |
| **`FieldStrategy.ALWAYS`** | 否则 null 字段不会写进 UPDATE，`active_flag` 置不空 |
| **"一人一单"的真义** | 同时最多 1 个**有效**订单，不是一辈子只能买一次 |
| **必对齐的 4 处** | Redis Set / 消费者查重 / 唯一索引 / 关单更新 |
| **`getOne` 的坑** | 查到多条会抛 `TooManyResultsException` → 接口 500；加 `LIMIT 1` 兜住 |
| **RR 快照的坑** ⭐ | **事务内的普通 SELECT 读的是事务开始时的快照，看不到别人新提交的数据** |
| **当前读 vs 快照读** | `SELECT` 读快照；`SELECT ... FOR UPDATE` / `UPDATE` 读最新 |
| **`@EnableScheduling`** | 不加则定时任务静默不执行 |
| **批量处理要 try-catch** | 单条失败不能中断整体 |
| **并发测试要跑多次** | 一次通过说明不了任何问题，10 次 0 失败才有说服力 |
| **提交顺序控制不了胜负** | `submit` 顺序只决定谁先进线程池，真正的赛点由调度决定 |
