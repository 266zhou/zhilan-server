## 2. 第 0 步：概念课（必读）

**这一节不看懂，后面代码你只能照抄。** 认真读 10 分钟。

### 2.1 为什么需要缓存

看一组数量级对比（不同机器有差异，但量级关系不变）：

| 存储 | 典型读取耗时 | 大概量级 |
|---|---|---|
| **Caffeine**（JVM 内存） | ~100 纳秒 | 最快 ⚡ |
| **Redis**（网络 + 内存） | ~1 毫秒 | 快 |
| **MySQL**（磁盘 IO + SQL 解析） | ~10 毫秒 | 慢 |

也就是说：**Redis 比 MySQL 快约 10 倍，Caffeine 比 Redis 快约 10000 倍。**

更重要的是**吞吐能力**：单机 MySQL 大概能扛几千 QPS，而 Redis 能扛 10 万+ QPS。

**所以缓存的核心价值有两个**：
1. **让接口变快**（用户体验）
2. **保护数据库不被打垮**（系统稳定性）← 这个其实更重要

### 2.2 缓存的读写模式：Cache Aside

业界最常用的缓存模式叫 **Cache Aside（旁路缓存）**，就两句话：

```
【读数据】
  1. 先查缓存 → 命中就返回
  2. 没命中 → 查数据库
  3. 把查到的结果写回缓存 → 返回

【写数据】
  1. 先更新数据库
  2. 再删除缓存（⚠️ 是删除，不是更新！）
```

**⚠️ 关键问题：为什么写数据时是"删除缓存"，而不是"更新缓存"？**

三个原因，都要理解：

| 原因 | 说明 |
|---|---|
| **① 可能白更新** | 你更新了缓存，但这条数据接下来根本没人读 → 白白浪费一次写操作 |
| **② 并发写会脏** | 两个线程同时更新，缓存可能被"后执行的旧值"覆盖 → 数据变脏 |
| **③ 删除更简单** | 删掉就完事，下次有人读的时候自然会从数据库加载最新值（**懒加载**） |

**记住这句话**：**更新数据库后删缓存。** 后面我们所有的写操作都遵循这个原则。

### 2.3 三大经典问题（面试必考）

#### 🔴 问题一：缓存穿透（Cache Penetration）

**场景**：有人故意请求一个**数据库里根本不存在**的数据，比如 `GET /shop/-1`、`GET /shop/99999999`。

**为什么会出事**：
```
请求 id=-1
  → 查 Caffeine：没有
  → 查 Redis：没有（因为数据本来就不存在，永远存不进去）
  → 查 MySQL：没有
  → 返回 null
下一次请求 id=-1，又是同样的流程……
```

**注意关键点**：因为数据不存在，**缓存里永远不会有它**，所以每次请求都会**穿透缓存直达数据库**。

如果有人用脚本每秒发 10 万个 `id=-1` 的请求，你的数据库瞬间就被打挂了。

**解法**：

| 方案 | 说明 | 本项目是否采用 |
|---|---|---|
| **缓存空值** | 数据库查不到时，也往 Redis 存一个空值（比如 `""`），下次直接返回 | ✅ 采用 |
| 布隆过滤器 | 用位数组提前判断"这个 key 一定不存在"，直接拦掉 | 进阶（暂不做） |

#### 🟠 问题二：缓存击穿（Cache Breakdown）

**场景**：某个**热点 key**（比如首页那个爆款商家）**突然过期了**。

**为什么会出事**：
```
热点 key "cache:shop:1" 在 00:00:00 过期
         ↓
同一瞬间，有 10000 个请求都在查 shop:1
         ↓
10000 个请求缓存全部未命中
         ↓
10000 个请求【同时】冲进数据库执行 SELECT
         ↓
数据库瞬间压力暴涨 💥
```

**注意和穿透的区别**：**击穿的数据是存在的**，只是"过期那一瞬间"出了问题。而且它只涉及**个别热点 key**。

**解法**：

| 方案 | 思路 | 本项目 |
|---|---|---|
| **互斥锁** | 只让 1 个线程去查数据库重建缓存，其他线程等待 | |
| **逻辑过期** | Redis 里永不过期，过期时间存在数据内部；发现逻辑过期就让 1 个线程**异步**重建，其他线程**返回旧数据** | ✅ 采用 |

**为什么选逻辑过期？** 因为互斥锁方案下，其他线程要**等待**（用户要等）；而逻辑过期方案下，所有线程都**立刻拿到旧数据**，用户体验丝滑。代价是**会有短暂的数据不一致**（旧数据），需要业务上能接受。

#### 🟡 问题三：缓存雪崩（Cache Avalanche）

**场景**：**大量 key 在同一时刻集体过期**。

比如你给所有缓存都设了 30 分钟 TTL，如果在某个时间点批量写入了 10000 条缓存，那么 30 分钟后它们会**同时失效**，请求全部涌向数据库。

**注意和击穿的区别**：击穿是"**一个**热点 key"，雪崩是"**一大批** key"。

**解法**：

| 方案 | 说明 | 本项目 |
|---|---|---|
| **TTL 加随机值** | 过期时间 = 30分钟 + 随机0~60秒，把过期时间"打散" | ✅ 采用 |
| 多级缓存 | Caffeine 崩了还有 Redis 顶着 | ✅ 采用 |
| 缓存永不过期 | 配合逻辑过期使用 | ✅ 采用 |

#### 📊 三者对比（一定要记牢）

| | 缓存穿透 | 缓存击穿 | 缓存雪崩 |
|---|---|---|---|
| **数据是否存在** | ❌ 不存在 | ✅ 存在 | ✅ 存在 |
| **涉及范围** | 任意"不存在"的 key | **单个**热点 key | **大批量** key |
| **触发原因** | 恶意/错误请求 | 热点 key 过期瞬间 | 大量 key 同时过期 |
| **直接后果** | 每次都打库 | 瞬间打库 | 数据库整体崩 |
| **解法** | 空值缓存、布隆过滤器 | 互斥锁、逻辑过期 | TTL 随机、多级缓存 |

### 2.4 什么是"多级缓存"

```
       请求
        │
        ▼
┌───────────────────┐
│  L1: Caffeine     │  JVM 进程内内存 · 纳秒级 · 最快
│  （本地缓存）      │  ⚠️ 每个实例各存一份，多实例之间不同步
└────────┬──────────┘
         │ 未命中
         ▼
┌───────────────────┐
│  L2: Redis        │  集中式 · 毫秒级 · 多实例共享
│  （分布式缓存）    │  ⚠️ 有网络开销
└────────┬──────────┘
         │ 未命中
         ▼
┌───────────────────┐
│  L3: MySQL        │  磁盘 · 10 毫秒级 · 最慢
└───────────────────┘
```

**为什么要两级？**
- Caffeine 极快，能挡掉绝大部分请求，**几乎不给 Redis 压力**
- Redis 作为"共享的第二道防线"，挡住 Caffeine 没命中的请求

**代价（要知道）**：Caffeine 是**进程内**的，如果你部署了 3 个实例，就有 3 份独立的 Caffeine。**更新数据时必须让 3 个实例的 Caffeine 都失效**——这就需要额外机制（比如 Redis 发布订阅、MQ 广播）。本阶段我们先做单机版本，并在第 8 步说明这个问题。

### 2.5 本阶段任务总览

| 要做的 | 用到的技术 | 对应简历描述 |
|---|---|---|
| 二级缓存 | Caffeine + Redis | 多级缓存 |

## 3. 第 1 步：RedisKeyConstants 常量类

### 为什么需要它

如果你在每个地方都手写 `"cache:shop:"`，那么：
- 写错一个字符（`"cache:shpo:"`）→ 缓存永远不命中，而且**不报错**，极难排查
- 哪天要改前缀，得全局搜索替换

**集中管理 key，是缓存相关的第一个好习惯。**

### 代码

新建 `com/zhilan/zhilanserver/constant/RedisKeyConstants.java`：

```java
package com.zhilan.zhilanserver.constant;

/**
 * Redis Key 前缀常量
 */
public final class RedisKeyConstants {

    /** 工具类，禁止实例化 */
    private RedisKeyConstants() {
    }

    /** 商家详情缓存：cache:shop:{id} */
    public static final String CACHE_SHOP_KEY = "cache:shop:";

    /** 商家详情缓存逻辑过期时间（秒） */
    public static final Long CACHE_SHOP_TTL = 1800L;
}
```

### 讲解

**`public final class` + 私有构造方法**：这是 Java 里写"常量类"的标准做法。
- `final` 表示这个类**不能被继承**
- 私有构造方法表示**不能被 `new`**（工具类不需要实例，只能通过 `RedisKeyConstants.CACHE_SHOP_KEY` 访问）

**key 的命名规范**：`业务:类型:标识`
- `cache:shop:1` → 缓存、商家、id=1

**为什么用冒号分隔？** 这是 Redis 社区的通用约定（不是语法要求），好处是在 Redis 客户端里能**按层级分组显示**，一眼看出结构。

## 4. 第 2 步：RedisData 逻辑过期包装类

### 为什么需要它

**先理解"逻辑过期"和"物理过期"的区别**，这是本阶段最重要的概念：

| | 物理过期（普通缓存） | 逻辑过期 |
|---|---|---|
| **怎么实现** | 给 Redis key 设置 TTL | **不设 TTL**（key 永不过期），把过期时间**存在 value 里面** |
| **到期时** | Redis **自动删除** key | key **还在**，只是数据里的 `expireTime` 已经过去了 |
| **到期后请求** | 缓存未命中 → 查数据库（**所有人一起查** 💥） | 缓存**命中**（能拿到旧数据）→ 判断逻辑过期 → 只让 **1 个线程**去重建，其他返回旧数据 ✅ |

**关键洞察**：物理过期时，key 被删了，**多个线程同时发现"没缓存"**，就会一起冲向数据库。
逻辑过期时，key 一直存在，程序**自己判断**是否"逻辑过期"，于是可以从容地**只放一个线程**去重建。

**所以我们需要一个"包装类"**，把"过期时间"和"真实数据"打包在一起存进 Redis：

```json
{
  "expireTime": "2026-10-12T22:30:00",
  "data": { "id": 1, "name": "老王火锅", "type": "美食", ... }
}
```

### 代码

新建 `com/zhilan/zhilanserver/common/RedisData.java`：

```java
package com.zhilan.zhilanserver.common;

import lombok.Data;

import java.io.Serializable;
import java.time.LocalDateTime;

/**
 * 逻辑过期包装类：把「逻辑过期时间」和「真实数据」一起缓存
 *
 * @param <T> 真实数据的类型
 */
@Data
public class RedisData<T> implements Serializable {

    /** 逻辑过期时间：Redis 里的 key 本身永不过期，靠这个字段判断"逻辑上是否过期" */
    private LocalDateTime expireTime;

    /** 真实业务数据 */
    private T data;
}
```

### 讲解

**泛型 `<T>`**：和阶段 1 的 `Result<T>` 一个道理。`RedisData<Shop>` 的 `data` 就是 `Shop`，`RedisData<Voucher>` 就是 `Voucher`。

**`LocalDateTime`**：Java 8 的新时间 API，比老的 `Date` 好用。后面序列化时，Spring Boot 会自动把它转成 ISO 格式字符串，比如 `2026-10-12T22:30:00`。

## 5. 第 3 步：CaffeineConfig 一级缓存

### 什么是 Caffeine

Caffeine 是 Java 里**性能最强的本地缓存库**（Spring Boot 官方推荐，取代了老牌的 Guava Cache）。

**"本地缓存"的意思**：数据存在**当前 JVM 进程的内存**里，不经过网络，所以纳秒级读取。

### 代码

新建 `com/zhilan/zhilanserver/config/CaffeineConfig.java`：

```java
package com.zhilan.zhilanserver.config;

import com.github.benmanes.caffeine.cache.Cache;
import com.github.benmanes.caffeine.cache.Caffeine;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import java.util.concurrent.TimeUnit;

/**
 * Caffeine 本地缓存（一级缓存）配置
 */
@Configuration
public class CaffeineConfig {

    /**
     * 全局共用一个本地缓存容器
     */
    @Bean
    public Cache<String, Object> localCache() {
        return Caffeine.newBuilder()
                // 初始容量：预估能存多少条，避免反复扩容
                .initialCapacity(100)
                // 最大容量：超过后按 LRU 淘汰，防止内存无限增长 ⚠️ 必须设置
                .maximumSize(1000)
                // 写入后 10 分钟过期
                .expireAfterWrite(10, TimeUnit.MINUTES)
                .build();
    }
}
```

### 逐行讲解

**`@Configuration` + `@Bean`**：和阶段 1 的 `MybatisPlusConfig` 一样，把这个对象交给 Spring 管理。之后在任何地方 `@Autowired` / 构造注入 `Cache<String, Object>` 就能拿到它。

**⚠️ `maximumSize` 必须设置！**
如果不设上限，Caffeine 会一直往内存里塞数据，最终导致 **OOM（内存溢出）**，整个应用崩掉。**这是本地缓存的第一大坑。**

**`expireAfterWrite(10, MINUTES)`**：写入 10 分钟后自动失效。
**为什么要 10 分钟？** 因为本地缓存**无法被其他实例感知**，TTL 短一点能减小数据不一致的窗口。

**Caffeine 常用的三种淘汰策略**（了解即可）：

| 方法 | 含义 |
|---|---|
| `expireAfterWrite` | **写入**后多久过期（我们用这个） |
| `expireAfterAccess` | **最后一次访问**后多久过期（读得多就活得久） |
| `maximumSize` | 最多多少条（LRU 淘汰） |

**关于 `Cache<String, Object>` 这个 Bean**：
`Object` 表示"什么都能存"。因为它是给 `CacheClient` 通用的，不限定类型。取出来时再自己转成需要的类型。

> ⚠️ **导入别导错**：要用 `com.github.benmanes.caffeine.cache.Cache`，
> 不要用 Spring 自带的 `org.springframework.cache.Cache`（同名，容易点错）。

## 6. 第 4 步：CacheClient 核心工具类

**这是本阶段的核心。** 我们把"读缓存的套路"和"写缓存的套路"封装成一个通用工具类，之后所有业务都能复用。

### 6.1 设计预览

先看我们要提供哪些方法，理解整体设计：

| 方法 | 作用 | 解决的问题 |
|---|---|---|
| `set(key, value, time, unit)` | 写普通缓存（带 TTL） | 基础能力 + **防雪崩**（TTL 随机） |
| `setWithLogicalExpire(...)` | 写逻辑过期缓存 | 逻辑过期的基础 |
| `delete(key)` | 删除缓存（Redis + Caffeine 都删） | **数据一致性** |
| `queryWithPassThrough(...)` | 查询：Caffeine → Redis → DB，带空值缓存 | **多级缓存 + 防穿透** |
| `queryWithLogicalExpire(...)` | 查询：带逻辑过期 + 互斥锁 + 异步重建 | **防击穿** |

**两个查询方法的差别**（很重要，先记住）：

- `queryWithPassThrough`：**简单版**，缓存会真正过期，适合**非热点**数据
- `queryWithLogicalExpire`：**进阶版**，缓存逻辑上过期，适合**热点**数据

> 商家详情属于热点数据，所以最终 `getDetail` 会用 **`queryWithLogicalExpire`**。
> `queryWithPassThrough` 作为"简单场景"的备用方案保留在工具类里——**工具类提供多种策略是正常的设计**，你在教程后面会看到两者的对比。

### 6.2 一个重要的技术选型：为什么用 StringRedisTemplate + ObjectMapper

阶段 1 你写过一个 `RedisConfig`，里面用的是 `RedisTemplate<String, Object>` + `GenericJackson2JsonRedisSerializer`。

**阶段 2 我们换个更清爽的方案**：`StringRedisTemplate` + 注入 Spring Boot 的 `ObjectMapper`。

**为什么？** 对比一下：

| 方案 | 存进 Redis 的样子 | 问题 |
|---|---|---|
| `GenericJackson2JsonRedisSerializer` | `{"@class":"com.zhilan...Shop","id":1,...}` | ① JSON 里混入了 `@class` 元数据，不干净 ② `LocalDateTime` 需要额外配置才支持序列化，**不配置会直接报错** |
| **`StringRedisTemplate` + `ObjectMapper`** | `{"id":1,"name":"老王火锅",...}` | 干净的 JSON，`redis-cli` 里一眼看懂；`ObjectMapper` 由 Spring Boot 自动配好（已支持 `LocalDateTime`） |

所以本阶段我们**手动序列化**：存的时候 `对象 → JSON 字符串`，取的时候 `JSON 字符串 → 对象`。

**这多出来的两行代码，换来的是：数据干净、类型完全可控、不会踩序列化坑。** 这是值得的。

> 你阶段 1 写的 `RedisConfig` **保留不动**，两个 Template 可以共存，互不影响。

### 6.3 完整代码

新建 `com/zhilan/zhilanserver/utils/CacheClient.java`：

```java
package com.zhilan.zhilanserver.utils;

import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.JavaType;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.github.benmanes.caffeine.cache.Cache;
import com.zhilan.zhilanserver.common.BusinessException;
import com.zhilan.zhilanserver.common.RedisData;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;

import java.time.LocalDateTime;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.ThreadLocalRandom;
import java.util.concurrent.TimeUnit;
import java.util.function.Function;

/**
 * 缓存工具类：封装 Redis + Caffeine 的常见读写模式
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class CacheClient {

    private final StringRedisTemplate stringRedisTemplate;
    private final ObjectMapper objectMapper;
    /** Caffeine 一级缓存 */
    private final Cache<String, Object> localCache;

    /** 异步重建缓存用的线程池（避免每次都 new Thread） */
    private static final ExecutorService CACHE_REBUILD_EXECUTOR = Executors.newFixedThreadPool(10);

    /** 空值缓存的 TTL（分钟）：防穿透用。不能太长，否则新增数据后会长期查不到 */
    private static final long NULL_CACHE_MINUTES = 2L;

    /** 重建锁的 TTL（秒）：防止拿到锁的线程挂掉导致锁永不释放 */
    private static final long LOCK_SECONDS = 10L;

    // ==================== 写入 ====================

    /**
     * 写缓存（带物理 TTL）
     * TTL 额外加 0~60 秒随机值 → 把过期时间"打散"，防止大量 key 同时失效（缓存雪崩）
     */
    public void set(String key, Object value, Long time, TimeUnit unit) {
        if (value == null) {
            return;
        }
        long ttlSeconds = unit.toSeconds(time) + ThreadLocalRandom.current().nextLong(60);
        stringRedisTemplate.opsForValue().set(key, toJson(value), ttlSeconds, TimeUnit.SECONDS);
        localCache.put(key, value);
        log.info("[缓存] 写入 key={}, ttl={}s", key, ttlSeconds);
    }

    /**
     * 写「逻辑过期」缓存：Redis 里的 key 永不过期，过期时间存在 value 内部
     */
    public void setWithLogicalExpire(String key, Object value, Long time, TimeUnit unit) {
        if (value == null) {
            return;
        }
        RedisData<Object> redisData = new RedisData<>();
        redisData.setData(value);
        redisData.setExpireTime(LocalDateTime.now().plusSeconds(unit.toSeconds(time)));

        stringRedisTemplate.opsForValue().set(key, toJson(redisData));
        localCache.put(key, redisData);
        log.info("[缓存] 写入逻辑过期缓存 key={}, 逻辑过期时间={}", key, redisData.getExpireTime());
    }

    /**
     * 删除缓存：一级和二级都要删
     */
    public void delete(String key) {
        stringRedisTemplate.delete(key);
        localCache.invalidate(key);
        log.info("[缓存] 删除 key={}", key);
    }

    // ==================== 查询 ====================

    /**
     * 查询缓存：Caffeine(一级) → Redis(二级) → 数据库
     * 特点：物理过期；用「空值缓存」防止缓存穿透
     *
     * @param keyPrefix  key 前缀，如 "cache:shop:"
     * @param id         业务 id
     * @param type       返回值的类型，用于反序列化
     * @param dbFallback 回源数据库的方法（查不到时怎么查库）
     * @param time       缓存有效期
     */
    public <R, ID> R queryWithPassThrough(String keyPrefix, ID id, Class<R> type,
                                          Function<ID, R> dbFallback,
                                          Long time, TimeUnit unit) {
        String key = keyPrefix + id;

        // ① 一级缓存：Caffeine
        Object cached = localCache.getIfPresent(key);
        if (cached != null) {
            log.info("[缓存] 一级(Caffeine)命中 key={}", key);
            return cast(cached);
        }

        // ② 二级缓存：Redis
        String json = stringRedisTemplate.opsForValue().get(key);
        if (json != null) {
            if (json.isEmpty()) {
                // 之前查过，数据库里确实没有 → 直接返回 null，不再打库（防穿透）
                log.info("[缓存] 二级(Redis)命中【空值】 key={} —— 防穿透生效", key);
                return null;
            }
            log.info("[缓存] 二级(Redis)命中 key={}", key);
            R value = fromJson(json, type);
            localCache.put(key, value);
            return value;
        }

        // ③ 都没命中：回源数据库
        log.info("[缓存] 未命中，回源数据库 key={}", key);
        R value = dbFallback.apply(id);

        if (value == null) {
            // 数据库也没有 → 缓存一个空值（TTL 要短）
            stringRedisTemplate.opsForValue().set(key, "", NULL_CACHE_MINUTES, TimeUnit.MINUTES);
            log.info("[缓存] 数据库无此数据，写入空值缓存 key={}", key);
            return null;
        }

        set(key, value, time, unit);
        return value;
    }

    /**
     * 查询缓存：防「缓存击穿」—— 逻辑过期 + 互斥锁 + 异步重建
     * 适合热点 Key：过期瞬间所有请求都能立刻拿到旧数据，只有 1 个线程去重建
     */
    public <R, ID> R queryWithLogicalExpire(String keyPrefix, ID id, Class<R> type,
                                            Function<ID, R> dbFallback,
                                            Long time, TimeUnit unit) {
        String key = keyPrefix + id;

        // ① 一级缓存：Caffeine
        Object cached = localCache.getIfPresent(key);
        if (cached instanceof RedisData<?> localData && !isLogicalExpired(localData)) {
            log.info("[缓存] 一级(Caffeine)命中 key={}", key);
            return cast(localData.getData());
        }

        // ② 二级缓存：Redis
        String json = stringRedisTemplate.opsForValue().get(key);

        // 2.1 完全没命中
        if (json == null || json.isEmpty()) {
            if (json != null) {
                // 命中的是空值 → 防穿透
                log.info("[缓存] 二级(Redis)命中【空值】 key={} —— 防穿透生效", key);
                return null;
            }
            // 真的没有：回源数据库（首次加载 / 缓存被删）
            log.info("[缓存] 未命中，回源数据库 key={}", key);
            R value = dbFallback.apply(id);
            if (value == null) {
                stringRedisTemplate.opsForValue().set(key, "", NULL_CACHE_MINUTES, TimeUnit.MINUTES);
                log.info("[缓存] 数据库无此数据，写入空值缓存 key={}", key);
                return null;
            }
            setWithLogicalExpire(key, value, time, unit);
            return value;
        }

        // 2.2 命中了，检查逻辑是否过期
        RedisData<R> redisData = fromJsonToRedisData(json, type);

        if (!isLogicalExpired(redisData)) {
            log.info("[缓存] 二级(Redis)命中且未过期 key={}", key);
            localCache.put(key, redisData);
            return redisData.getData();
        }

        // 2.3 逻辑已过期 → 抢锁重建
        log.info("[缓存] 二级(Redis)命中但【逻辑已过期】 key={}", key);
        String lockKey = "lock:" + key;

        if (tryLock(lockKey)) {
            // 抢到锁：交给线程池【异步】重建，当前请求先返回旧数据（用户不用等）
            CACHE_REBUILD_EXECUTOR.submit(() -> {
                try {
                    log.info("[缓存] 开始异步重建 key={}", key);
                    R fresh = dbFallback.apply(id);
                    if (fresh == null) {
                        stringRedisTemplate.opsForValue()
                                .set(key, "", NULL_CACHE_MINUTES, TimeUnit.MINUTES);
                        localCache.invalidate(key);
                    } else {
                        setWithLogicalExpire(key, fresh, time, unit);
                    }
                } catch (Exception e) {
                    log.error("[缓存] 重建失败 key={}", key, e);
                } finally {
                    unlock(lockKey);
                }
            });
        } else {
            log.info("[缓存] 没抢到重建锁，直接返回旧数据 key={}", key);
        }

        // 无论有没有抢到锁，都返回旧数据（这就是"逻辑过期"的核心：不阻塞用户）
        return redisData.getData();
    }

    // ==================== 私有辅助方法 ====================

    /** 判断逻辑是否已过期 */
    private boolean isLogicalExpired(RedisData<?> redisData) {
        return redisData.getExpireTime() == null
                || redisData.getExpireTime().isBefore(LocalDateTime.now());
    }

    /** 尝试加锁（setnx + 过期时间） */
    private boolean tryLock(String lockKey) {
        Boolean ok = stringRedisTemplate.opsForValue()
                .setIfAbsent(lockKey, "1", LOCK_SECONDS, TimeUnit.SECONDS);
        return Boolean.TRUE.equals(ok);
    }

    /** 释放锁 */
    private void unlock(String lockKey) {
        stringRedisTemplate.delete(lockKey);
    }

    /** 对象 → JSON */
    private String toJson(Object value) {
        try {
            return objectMapper.writeValueAsString(value);
        } catch (JsonProcessingException e) {
            log.error("[缓存] 序列化失败", e);
            throw new BusinessException("缓存序列化失败");
        }
    }

    /** JSON → 对象 */
    private <R> R fromJson(String json, Class<R> type) {
        try {
            return objectMapper.readValue(json, type);
        } catch (JsonProcessingException e) {
            log.error("[缓存] 反序列化失败 json={}", json, e);
            throw new BusinessException("缓存反序列化失败");
        }
    }

    /** JSON → RedisData&lt;R&gt;（带泛型，所以要构造 JavaType） */
    private <R> RedisData<R> fromJsonToRedisData(String json, Class<R> type) {
        try {
            JavaType javaType = objectMapper.getTypeFactory()
                    .constructParametricType(RedisData.class, type);
            return objectMapper.readValue(json, javaType);
        } catch (JsonProcessingException e) {
            log.error("[缓存] 反序列化失败 json={}", json, e);
            throw new BusinessException("缓存反序列化失败");
        }
    }

    @SuppressWarnings("unchecked")
    private <R> R cast(Object value) {
        return (R) value;
    }
}
```

### 6.4 逐块讲解（重点看）

#### ① 依赖注入的三个对象

```java
private final StringRedisTemplate stringRedisTemplate;
private final ObjectMapper objectMapper;
private final Cache<String, Object> localCache;
```

配合类上的 `@RequiredArgsConstructor`，Lombok 会生成一个包含这三个参数的构造方法，Spring 启动时自动把对应的 Bean 注入进来：
- `StringRedisTemplate` → Spring Boot 自动配置提供
- `ObjectMapper` → Spring Boot 自动配置提供（**已注册 JavaTimeModule，所以能处理 `LocalDateTime`**）
- `Cache<String, Object>` → 我们在第 3 步自己声明的 `CaffeineConfig`

#### ② 防雪崩：TTL 加随机值

```java
long ttlSeconds = unit.toSeconds(time) + ThreadLocalRandom.current().nextLong(60);
```

`ThreadLocalRandom.current().nextLong(60)` 生成 `[0, 60)` 的随机数。

**效果**：原本所有 key 都在 30 分钟整点过期；现在变成 30 分 00 秒 ~ 30 分 59 秒之间**分散**过期，数据库不会被同时冲击。**一行代码解决雪崩的一大半。**

> 为什么用 `ThreadLocalRandom` 而不是 `Math.random()`？
> `ThreadLocalRandom` 在多线程下**没有竞争**，性能更好。JDK 7+ 推荐用法。

#### ③ 空值缓存（防穿透）的关键细节

```java
if (json.isEmpty()) {
    log.info("[缓存] 二级(Redis)命中【空值】 key={}", key);
    return null;
}
```

**这里有个极易出错的地方**：`StringRedisTemplate.get()` 返回 **null** 和返回 **空字符串 `""`** 是两件事！

| 返回值 | 含义 |
|---|---|
| `null` | Redis 里**没有这个 key**（真未命中） |
| `""`（空字符串） | Redis 里**有这个 key**，值是空的 → 说明我们之前查过，**数据库里确实不存在** |

**如果搞混，防穿透就完全失效了。** 所以判断顺序必须是：先判 `null`（真未命中），再判 `isEmpty()`（命中空值）。

#### ④ 逻辑过期的完整流程（本阶段最难的一段）

```
queryWithLogicalExpire(key):
  │
  ├─ ① Caffeine 有，且未逻辑过期 ──────────────► 返回（纳秒级）
  │
  ├─ ② Redis 没有 / 是空值 ───────────────────► 回源DB → 写逻辑过期缓存 / 写空值
  │
  └─ ③ Redis 命中
        ├─ 未逻辑过期 ───────────────────────► 回填 Caffeine，返回
        └─ 已逻辑过期
              ├─ 抢到锁 ──► 提交线程池【异步重建】
              │              └─ 当前请求【返回旧数据】
              └─ 没抢到 ──► 直接【返回旧数据】
```

**核心设计思想**（理解这句就懂逻辑过期了）：

> **"先用旧的，再偷偷换新的。"**
>
> 用户永远立刻拿到数据（哪怕是旧的），**没有任何等待**；
> 同时系统在后台悄悄把最新数据加载好。
> 这样就避免了"1 万个请求同时冲向数据库"。

**几个细节**：

**为什么重建要用线程池，而不是 `new Thread()`？**
每次创建线程开销很大，而且无法控制数量。用**固定大小（10 个）的线程池**，既能并发重建，又不会把系统资源耗光。

**为什么最后 `return redisData.getData()`，而不是等重建完再返回？**
因为一旦等待，就退化成"互斥锁方案"了，用户要等。**逻辑过期的价值就在于"不等待"。**

**`finally { unlock(lockKey); }` 为什么必须有？**
不管重建成功还是失败，锁**必须释放**。否则后面所有请求都抢不到锁，缓存永远无法重建。

**⚠️ 一个已知的简化点**：这里的 `unlock` 直接 `delete` 了 key，严格来说有隐患——如果 A 线程重建耗时超过 10 秒，锁自动过期了，B 线程拿到新锁，此时 A 再执行 `unlock` 会把 B 的锁误删。**生产环境要用「Lua 脚本 + 唯一值」来安全释放锁**（判断"这把锁是不是我加的"再删）。我们会在**阶段 3 秒杀**里学这个技巧。

#### ⑤ 泛型方法和 `Function` 回调

```java
public <R, ID> R queryWithPassThrough(String keyPrefix, ID id, Class<R> type,
                                      Function<ID, R> dbFallback, ...)
```

为什么这么设计？因为 `CacheClient` 要**通用**——今天缓存 `Shop`，明天要缓存 `Voucher`。

**`Function<ID, R> dbFallback` 是什么？**
这是 Java 8 的**函数式接口**：`Function<入参类型, 返回值类型>`。意思是"**你给我一个方法，告诉我怎么查数据库，我来调用它**"。

调用时会写成这样（下一节你会看到）：

```java
cacheClient.queryWithPassThrough(
    RedisKeyConstants.CACHE_SHOP_KEY, id, Shop.class,
    this::getById,          // ← 把"怎么查库"传进去
    30L, TimeUnit.MINUTES);
```

`this::getById` 是**方法引用**，等价于 `id -> this.getById(id)`。

**这个设计的好处**：`CacheClient` 完全不需要知道"Shop 表长什么样"、"用什么 SQL 查"，它只管**缓存逻辑**；查库的活儿由调用方通过 `dbFallback` 提供。**这就是"关注点分离"。**

#### ⑥ 序列化的泛型处理

```java
JavaType javaType = objectMapper.getTypeFactory()
        .constructParametricType(RedisData.class, type);
return objectMapper.readValue(json, javaType);
```

**为什么不能直接 `objectMapper.readValue(json, RedisData.class)`？**

因为 Java 有**泛型擦除**——运行时 `RedisData<Shop>` 和 `RedisData` 是同一个类。如果只传 `RedisData.class`，Jackson 不知道 `data` 字段应该转成什么类型，会给你一个 `LinkedHashMap`，后面强转成 `Shop` 就抛 `ClassCastException`。

**`constructParametricType(RedisData.class, type)`** 就是显式告诉 Jackson：**"请按 `RedisData<Shop>` 来解析"**。

这是个很实用的技巧，以后遇到"泛型对象反序列化"的问题都能用。

```java
@Override
public Shop getDetail(Long id) {
    if (id == null || id <= 0) {
        throw new BusinessException(400, "商家ID不合法");
    }

    Shop shop = cacheClient.queryWithLogicalExpire(
            RedisKeyConstants.CACHE_SHOP_KEY,   // key 前缀
            id,                                 // 业务 id
            Shop.class,                         // 返回类型
            this::getById,                      // 回源方法：查不到时怎么查库

```

**改成这样之后，`getDetail` 从 10 行变成了"一行调用"**，所有缓存逻辑（多级缓存、防穿透、防击穿）都被 `CacheClient` 承包了。

> **而 Controller 一行都不用改。** 这就是分层的价值。

### 7.3 新增/更新/删除时清理缓存

**按照 Cache Aside 模式：更新数据库后，必须删掉缓存。**

```java
@Override
public Long createShop(Shop shop) {
    shop.setId(null);
    shop.setSales(shop.getSales() == null ? 0 : shop.getSales());
    shop.setComments(shop.getComments() == null ? 0 : shop.getComments());
    shop.setStatus(shop.getStatus() == null ? 1 : shop.getStatus());
    save(shop);
    return shop.getId();
}

@Override
@Transactional(rollbackFor = Exception.class)
public void updateShop(Shop shop) {
    if (shop.getId() == null) {
        throw new BusinessException(400, "id 不能为空");
    }
    // ① 先更新数据库
    updateById(shop);
    // ② 再删除缓存（Cache Aside）
    cacheClient.delete(RedisKeyConstants.CACHE_SHOP_KEY + shop.getId());
}

@Override
@Transactional(rollbackFor = Exception.class)
public void deleteShop(Long id) {
    if (id == null || id <= 0) {
        throw new BusinessException(400, "商家ID不合法");
    }
    removeById(id);
    cacheClient.delete(RedisKeyConstants.CACHE_SHOP_KEY + id);
}
```

### 7.4 讲解

#### 为什么把逻辑从 Controller 挪进 Service（重要）

阶段 1 里，"统计 sales 默认值""更新后删缓存"这类逻辑都写在 Controller 里。**这在架构上是错的**：

| 层 | 该做什么 |
|---|---|
| Controller | 接参数、返回结果 |
| **Service** | **业务逻辑、事务、缓存** ← 这些属于业务规则 |

**挪过来的三个好处**：
1. **缓存和数据库操作在同一个事务里**（`@Transactional` 起作用）
2. 其他地方（比如定时任务、消息消费者）要复用这个逻辑时，直接调 Service 就行
3. Controller 变得极薄

#### `@Transactional(rollbackFor = Exception.class)` 讲解

**作用**：把方法里的多个数据库操作打包成**一个事务**——要么全成功，要么全失败回滚。

**`rollbackFor = Exception.class` 为什么必须写？**
Spring 默认**只在遇到 `RuntimeException` 时回滚**。如果抛出的是受检异常（`Exception` 的子类但不是 `RuntimeException`），默认**不回滚**！这是个巨坑。写上 `rollbackFor = Exception.class` 表示"**任何异常都回滚**"。

> 虽然我们这里两个操作手动控制，但这是好习惯。阶段 4 的支付、阶段 3 的秒杀都会重度依赖事务。

#### ⚠️ 一个注意点：删缓存应该在事务提交之后

严格来说，`cacheClient.delete()` 写在事务方法内部，会**在事务提交之前**执行。极端情况下：
```
T1: 删缓存 → T2: 读库（读到旧值）→ T2: 写回缓存（旧值）→ T1: 提交事务
结果：缓存里是旧数据，直到 TTL 过期
```

**更严谨的做法是"事务提交后再删缓存"**。本阶段先用简单版（TTL 兜底能最终修正），第 8 步会讲优化方案。

#### 为什么 `createShop` 不需要删缓存？

因为是**新增**，id 是新的，缓存里本来就**不可能有这个 id 的数据**，所以不需要处理。

### 7.5 ShopServiceImpl 完整代码

```java
package com.zhilan.zhilanserver.service.impl;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.baomidou.mybatisplus.extension.plugins.pagination.Page;
import com.baomidou.mybatisplus.extension.service.impl.ServiceImpl;
import com.zhilan.zhilanserver.common.BusinessException;
import com.zhilan.zhilanserver.dto.ShopQueryDTO;
import com.zhilan.zhilanserver.entity.Shop;
import com.zhilan.zhilanserver.mapper.ShopMapper;
import com.zhilan.zhilanserver.service.ShopService;
import com.zhilan.zhilanserver.utils.CacheClient;
import lombok.RequiredArgsConstructor;
import org.apache.commons.lang3.StringUtils;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.Set;
import java.util.concurrent.TimeUnit;

@Service
@RequiredArgsConstructor
public class ShopServiceImpl extends ServiceImpl<ShopMapper, Shop> implements ShopService {

   private final CacheClient cacheClient;

   private static final Set<String> SORT_FIELDS = Set.of("score", "sales", "avgPrice");

   @Override
   public Page<Shop> pageQuery(ShopQueryDTO query) {
      int page = query.getPage() == null || query.getPage() < 1 ? 1 : query.getPage();
      int pageSize = query.getPageSize() == null || query.getPageSize() < 1 ? 10
              : Math.min(query.getPageSize(), 100);

      LambdaQueryWrapper<Shop> wrapper = new LambdaQueryWrapper<>();
      wrapper.eq(StringUtils.isNotBlank(query.getType()), Shop::getType, query.getType())
              .eq(StringUtils.isNotBlank(query.getCity()), Shop::getCity, query.getCity())
              .eq(query.getStatus() != null, Shop::getStatus, query.getStatus())
              .and(StringUtils.isNotBlank(query.getKeyword()), w -> w
                      .like(Shop::getName, query.getKeyword())
                      .or()
                      .like(Shop::getAddress, query.getKeyword()));

      String sortBy = query.getSortBy();
      boolean asc = Boolean.TRUE.equals(query.getAsc());
      if (StringUtils.isNotBlank(sortBy) && SORT_FIELDS.contains(sortBy)) {
         switch (sortBy) {
            case "score" -> wrapper.orderBy(true, asc, Shop::getScore);
            case "sales" -> wrapper.orderBy(true, asc, Shop::getSales);
            case "avgPrice" -> wrapper.orderBy(true, asc, Shop::getAvgPrice);
            default -> wrapper.orderByDesc(Shop::getId);
         }
      } else {
         wrapper.orderByDesc(Shop::getId);
      }
      return page(new Page<>(page, pageSize), wrapper);
   }

   @Override
   public Shop getDetail(Long id) {
      if (id == null || id <= 0) {
         throw new BusinessException(400, "商家ID不合法");
      }
      Shop shop = cacheClient.queryWithLogicalExpire(
              RedisKeyConstants.CACHE_SHOP_KEY,
              id,
              Shop.class,
              this::getById,
              RedisKeyConstants.CACHE_SHOP_TTL,
              TimeUnit.SECONDS);
      if (shop == null) {
         throw new BusinessException(404, "商家不存在或已下架");
      }
      return shop;
   }

   @Override
   public Long createShop(Shop shop) {
      shop.setId(null);
      shop.setSales(shop.getSales() == null ? 0 : shop.getSales());
      shop.setComments(shop.getComments() == null ? 0 : shop.getComments());
      shop.setStatus(shop.getStatus() == null ? 1 : shop.getStatus());
      save(shop);
      return shop.getId();
   }

   @Override
   @Transactional(rollbackFor = Exception.class)
   public void updateShop(Shop shop) {
      if (shop.getId() == null) {
         throw new BusinessException(400, "id 不能为空");
      }
      updateById(shop);
      cacheClient.delete(RedisKeyConstants.CACHE_SHOP_KEY + shop.getId());
   }

   @Override
   @Transactional(rollbackFor = Exception.class)
   public void deleteShop(Long id) {
      if (id == null || id <= 0) {
         throw new BusinessException(400, "商家ID不合法");
      }
      removeById(id);
      cacheClient.delete(RedisKeyConstants.CACHE_SHOP_KEY + id);
   }
}
```

**对比一下阶段 1 的写法**：

```java
// 阶段 1：业务逻辑堆在 Controller 里
@PutMapping
public Result<Void> update(@RequestBody Shop shop) {
    if (shop.getId() == null) {
        return Result.fail(400, "id 不能为空");     // ← 参数校验逻辑
    }
    shopService.updateById(shop);                  // ← 直接调通用方法
    return Result.ok();
}

// 阶段 2：Controller 只负责"转发"
@PutMapping
public Result<Void> update(@RequestBody Shop shop) {
    shopService.updateShop(shop);   // ← 业务都在 Service 里
    return Result.ok();
}
```

**为什么要这样改？** 因为"更新后要删缓存"属于**业务规则**，如果留在 Controller 里，那么以后定时任务、MQ 消费者想更新商家时，就必须重新实现一遍删缓存——**迟早会漏**。放进 Service，所有人调用都自动带上缓存处理。

> `page` 和 `detail` 两个接口**完全不用改**，因为它们的签名没变化。

## 10. 第 8 步：一致性进阶

这一节讲"知道就行、以后优化"的内容。**面试常问，理解思路比写代码重要。**

### 10.1 删缓存失败了怎么办（三层防线）

`cacheClient.delete()` 可能会失败（Redis 网络抖动、Redis 挂了）。如果删失败，缓存里就是**旧数据**，用户会一直看到错的。

**三层防线**：

| 防线 | 做法 | 效果 |
|---|---|---|
| **第一层** | 更新数据库后**立即**删缓存 | 正常情况下就够了 |
| **第二层** | 删失败就**重试**（或发 MQ 异步补偿重试） | 兜住 Redis 短暂抖动 |
| **第三层** | 缓存**设置 TTL** | 最坏情况下的最终兜底 |

**我们的实现现状**：
- ✅ 第一层：已有（`cacheClient.delete()`）
- ⚠️ 第二层：**还没做** → 阶段 3 会用 RabbitMQ 实现"删除失败 → 发消息 → 消费者重试"
- ⚠️ 第三层：逻辑过期的缓存**没有物理 TTL**！

**⚠️ 所以这里有个问题需要你意识到**：
用逻辑过期方案后，Redis 里的 key **永不过期**。如果删除缓存失败，就**真的永远不一致了**（没有 TTL 兜底）。

**生产上的解决办法**：
- 给逻辑过期的 key **额外加一个较长的物理 TTL**（比如 24 小时），作为最终兜底
- 或者用 MQ 补偿确保删除一定成功

**本项目的选择**：阶段 3 用 RabbitMQ 做补偿重试（对应简历里的"若删除失败消息队列补偿重试"）。这也是为什么我把这一层放到阶段 3——那时候我们正好要搭 RabbitMQ。

### 10.2 更严谨的删除时机：事务提交后删

前面提过的问题：`delete` 写在事务方法里，会在**事务提交前**执行，存在极小的脏数据窗口。

**解决办法**（了解即可）：

```java
// 注册一个"事务提交后执行"的回调
TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                cacheClient.delete(key);
            }
        });
```

**思路**：把删缓存的动作**推迟到事务确认提交之后**。这样就不会出现"缓存删了、但事务最后回滚了"的尴尬。

### 10.3 延迟双删

另一种常见方案：更新数据库后删缓存，**过一会儿（比如 500ms）再删一次**。

**为什么？** 为了清掉那个"在删除之后、事务提交之前"被其他线程写入的脏缓存。第二次删除把漏网的脏数据清掉。

**代价**：多一次删除、有延迟。**实际项目里更多用"事务提交后删 + TTL 兜底"，延迟双删用得少。**

### 10.4 Caffeine 的分布式问题（重要认知）

**问题**：Caffeine 是**进程内**缓存。如果你部署了 3 个实例（A、B、C），它们各有一份 Caffeine。

```
用户更新了 shop:1
  → A 实例删除了自己的 Caffeine 和 Redis
  → B、C 实例的 Caffeine 里【还是旧数据】
  → 打到 B、C 的请求会返回旧数据 ❌
```

**这是本地缓存天生的缺陷。** 解决方案：

| 方案 | 做法 |
|---|---|
| **Redis 发布订阅** | 删除缓存时往 Redis 频道发消息，所有实例订阅后清自己的 Caffeine |
| **MQ 广播** | 用 RabbitMQ 的 fanout 交换机广播失效消息 |
| **缩短 TTL** | 最简单，把 Caffeine TTL 设短（如 1 分钟），容忍短暂不一致 |

**本项目现状**：单机部署，问题不存在。**但要知道这个坑**——面试问"本地缓存怎么保证一致性"就是考这个。

| 报错 / 现象 | 原因 | 解决 |
|---|---|---|
| 启动报 `No qualifying bean of type 'Cache<String, Object>'` | `CaffeineConfig` 没建 / 没加 `@Configuration` | 检查第 3 步 |
| 启动报 `No qualifying bean of type 'CacheClient'` | `CacheClient` 没加 `@Component` | 检查注解 |
| 导入了 `org.springframework.cache.Cache` | 包导错了 | 改成 `com.github.benmanes.caffeine.cache.Cache` |
| `ClassCastException: LinkedHashMap cannot be cast to Shop` | 泛型反序列化没处理 | 确认用了 `constructParametricType` |
| `Java 8 date/time type LocalDateTime not supported` | `ObjectMapper` 没注册 JavaTimeModule | 确认注入的是 **Spring Boot 自动配置**的 `ObjectMapper`（不要自己 `new ObjectMapper()`） |
| 缓存**永远不命中**，每次都查库 | 写入和读取的 key 前缀不一致 | 检查是否都用了 `RedisKeyConstants.CACHE_SHOP_KEY` |
| 防穿透失效，每次都查库 | 把"空值"和"未命中"搞混了 | 注意区分 `json == null`（未命中）和 `json.isEmpty()`（命中空值） |
| 缓存里的时间是数字（如 `1730000000.123`） | `WRITE_DATES_AS_TIMESTAMPS` 没关 | Spring Boot 默认已关；若自己 new ObjectMapper 需手动 `disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)` |
| 更新后查询还是旧数据 | 忘了删缓存 / key 拼错 | 检查 `updateShop` 里的 `cacheClient.delete(...)` |
| `@Transactional` 不生效 | 方法不是 `public`，或同类内部调用 | 必须是 Spring 代理调用的 `public` 方法 |
| 应用启动报 `Connection refused` | Redis 没启动 | 启动 Redis 服务 |

### 11.3 调试技巧

沿用阶段 1 的三件套，缓存场景下特别有用：

**① 看日志**：`CacheClient` 里每个分支都打了 `log.info`，日志会**直接告诉你数据从哪一层来的**。
```
[缓存] 一级(Caffeine)命中        ← 最快路径
[缓存] 二级(Redis)命中           ← 中等
[缓存] 未命中，回源数据库        ← 最慢，需要关注
```

**② 断点**：在 `CacheClient.queryWithLogicalExpire` 里下断点，`F8` 一步步走，看它走了哪个分支。
用 `Alt+F8` 求值 `json`、`redisData.getExpireTime()`、`LocalDateTime.now()` 对比。

**③ 直接看 Redis**：最直观的手段。
```bash
redis-cli
> keys cache:shop:*              # 看有哪些缓存
> get cache:shop:1               # 看内容
> ttl cache:shop:1               # 看剩余时间（-1 表示永不过期）
> del cache:shop:1               # 手动删除，模拟缓存失效
> exists cache:shop:1            # 判断是否存在
```

**⭐ 一个超好用的技巧**：测试逻辑过期时，不用改代码等 30 分钟——**直接手动改 Redis 里的 expireTime**：

```bash
> get cache:shop:1
> set cache:shop:1 "{\"expireTime\":\"2020-01-01T00:00:00\",\"data\":{...原来的数据...}}"
```

改成过去的日期，下次请求就会立刻触发"逻辑过期"流程。

## 附录：本阶段涉及的知识点速查

| 概念 | 一句话 |
|---|---|
| Cache Aside | 读：缓存→库→回填；写：更新库→**删**缓存 |
| 缓存穿透 | 数据不存在，缓存永远不命中 → 空值缓存解决 |
| 缓存击穿 | 热点 key 过期瞬间被打穿 → 逻辑过期/互斥锁解决 |
| 缓存雪崩 | 大量 key 同时过期 → TTL 随机解决 |
| 逻辑过期 | key 永不过期，过期时间存 value 里，只让 1 个线程异步重建 |
| 多级缓存 | Caffeine（进程内，纳秒）+ Redis（集中式，毫秒） |
| 空值缓存 | 查不到也存个 `""`，TTL 要短（本项目 2 分钟） |
| TTL 随机 | `TTL + random(60)`，把过期时间打散 |
